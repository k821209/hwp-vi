# hwp-vi

터미널에서 한글(.hwp/.hwpx) 문서를 다룬다. `vi` 처럼 치고, 파이프에 꽂는다.
**AI 도 같은 문서를 고칠 수 있다** — `hwp api` 가 JSON 을 받는다.

HWP 는 도스에서 돌던 워드프로세서였다. 터미널에 없을 이유가 없다.

`vim-*` 이 아니라 `hwp-vi` 다 — **Vim 플러그인이 아니고** 독립 실행 파일이다.
`vi` 의 조작 방식을 빌렸을 뿐, vimscript 도 `.vimrc` 도 쓰지 않는다. 실행
파일 이름은 `hwp` 다.

## 설치

필요한 것은 Rust 와 `curl` 뿐이다. **HWP 라이브러리도, 한컴오피스도, JVM 도
필요 없다.** 리눅스·macOS·WSL 에서 돈다.

```bash
git clone https://github.com/k821209/hwp-vi.git && cd hwp-vi
./scripts/fetch-rhwp.sh      # 판독 백엔드를 핀대로 받는다 (sha256 확인)
cargo build --release
./target/release/hwp doctor  # 무엇이 준비됐는지 말해 준다
```

Rust 가 없거나 `command not found: cargo` 가 나오면
[다른 컴에서 시작하기](#다른-컴에서-시작하기)에 한 줄씩 적어 뒀다.

```bash
./target/release/hwp 문서.hwp        # 열어서 고친다
echo '{"file":"문서.hwpx","read":["text","tables"]}' | ./target/release/hwp api
```

## 이 도구가 다른 점 — 저장이 스스로를 검증한다

고친 것을 **쓰고 나서 다시 읽어 대조한다.** 기대한 모양과 다르면 원본을
건드리지 않고 멈춘다. `--force` 는 **없다** — 검증을 못 지난 저장을 사람이
밀어낼 수 있으면 그 장치는 없는 것과 같다.

대조하는 쪽은 우리 편집기가 아니라 **독립 증인**(문서를 처음부터 다시 세는
판독기)이다. 같은 코드로 쓰고 같은 코드로 확인하면 "맞다" 가 공짜로 나온다.

> 조용히 틀리는 쪽이 제일 비싸다. 백엔드를 고르며 시험한 판독기 중 하나는
> 82KB 문서에서 **23자만 뽑고 성공으로 보고**했다 — 읽다 실패하면 받는 쪽이
> 알지만, 적게 읽고 `ok` 라고 하면 모른다.

기획과 근거는 [PLAN.md](PLAN.md). **§8 이 현행 계획**이고 §0~§6 은 선행조사 전
초안이다. 이 README 는 **작업 일지**다 — 무엇을 어떻게 재서 그렇게 정했는지,
틀린 것까지 적는다. 길다.

## 쓰는 법은 한 줄이다

```bash
hwp 문서.hwp          # 고치기로 연다 — vi 처럼
hwp -R 문서.hwp       # 읽기만
```

`vi 파일` 과 같다. 옵션은 없다.

**아래 도움줄이 늘 있다.** 명령이 늘어나면 외우게 하는 대신 화면에 둬야 한다.
모드마다 다른 키를 말하고, **막혔을 때 가장 필요한 것이 맨 앞**이다 — `?`(도움)와
나가는 법. 처음엔 그 둘을 뒤에 뒀는데 90칸 터미널에서 먼저 잘렸다.

```
 읽기  ? 도움 · q 나가기 · jk ^d 이동 · ] [ 쪽 · / 찾기 · t 개요 · T 표 · z 그림
 고치기  ? 도움 · ZZ 저장하고 나가기 · i 넣기 · u 되돌리기 · x dd 지우기 · …
 표  ? 도움 · Esc 나가기 · hjkl 칸 · Tab 다음 칸 · T 다음 표
 끼워넣기  Esc 보통 모드로 · ⌫ 지우기 · :set ime=2 두벌식
```

알림줄은 **화면만 보고 알 수 없는 것**만 말한다 — 같은 키를 두 줄에 적지 않는다.

**`m`(또는 `F10`) 이 메뉴를 띄운다 — 화살표로 골라 실행한다.** 키를 외우지
않고도 무엇을 할 수 있는지 보고 고르는 자리다. 도움 보기(`?`)는 "키가
무엇인가" 를 말하고, 메뉴는 "지금 뭘 할까" 를 받는다. `F10` 은 도스 시절
편집기의 관례이고 HWP 도 거기서 왔다.

```
            ┌ 메뉴 ──────────────────────────────────┐
            │ 파일   편집   이동   보기              │
            │                                        │
            │ 되돌리기                               │   ← ↑↓ 로 고른다
            │ 다시하기                               │
            │ 단락 담기                              │
            │ 글머리 단계 들이기                     │
            │                                        │
            │ ↑↓ 고르기 · ←→ 묶음 · ↵ 실행 · Esc 닫기 │
            └────────────────────────────────────────┘
```

**메뉴가 곧 `Action` 을 낸다** — 키로 하던 길과 한 길이다. 메뉴만의 처리를
따로 쓰면 둘이 갈라지고, 메뉴로 한 일은 시험되지 않는다.

본문 **가운데에 작게** 띄운다. 화면을 다 덮으면 무엇에 대고 하는 일인지 보이지
않는다. 그래서 겹치는데, **한글이 상자 경계에 걸리면 테두리가 지워진다** —
두 칸짜리 글리프가 첫 칸은 상자 밖, 둘째 칸은 안에 있으면 글리프 전체가
그려지면서 `│` 를 덮는다. `Clear` 는 상자 안만 비우므로 경계 왼쪽의 2칸 글자를
따로 지운다. 라틴 글자만 쓰는 화면에서는 생기지 않는 일이다.

그리고 **`format!("{s:<10}")` 로 칸을 채우면 안 된다** — 글자 수로 채우므로
한글이 두 배가 되어 테두리를 넘는다. `wrap::pad_to` 가 표시 폭으로 채운다.
메뉴 항목을 그렇게 채웠다가 실제로 테두리가 사라졌다.

**`?` 가 전부 보여준다.** 도움줄 한 줄에 쉰 개가 넘는 키를 담을 수 없으니
두 칸으로 나눠 띄우고, 그래도 넘치면 **화살표로 넘긴다**(`↓ 더 있다` 를
오른쪽 아래에 적는다 — 잘린 채로 두면 "없는 기능" 으로 읽힌다). 뒤의 본문은 지운다 — 안 지우면 글자가 겹쳐 둘 다 못
읽는다(처음에 그렇게 나왔다). 도움줄은 남겨서 "어떻게 닫지" 가 화면에 남는다.

### 색

| | |
|---|---|
| 머리글 | 청록 바탕 |
| 모드 이름 | 초록 바탕 · 도움줄의 키는 노랑 |
| 쪽 경계·도움 테두리 | 파랑 |
| 단락 번호·표 테두리·그림 설명 | 어두운 회색 (글자보다 뒤로) |
| 점으로 그린 그림 | 초록 |
| 찾은 글자 | 노랑 바탕 |
| 저장 안 한 편집 | 노랑 바탕 |
| 개요 깊이 | 청록→초록→노랑→자홍 |

**색은 거들 뿐 뜻을 지지 않는다.** 흑백 터미널, 다른 테마, 색을 못 보는
사람이 모두 같은 정보를 읽어야 하므로 색만으로 말하지 않는다 — 쪽 경계는
선과 글자로, 지금 칸은 반전으로, 미저장은 글자로 이미 말한다.

`NO_COLOR` 가 있으면 전부 끈다([no-color.org](https://no-color.org) 의 관례 —
값은 보지 않고 있는지만 본다). 그때도 반전·굵기로 구분이 남는다.

**화면 안에서 바꾸는 것은 옵션이 아니라 키다.** 켜 보고 결정하는 값을 열기 전에
정하라고 하면 안 된다.

| 키 | |
|---|---|
| `z` | 그림 보기 방식 — 반블록 → 점자 → ASCII → 자리만 → 끔 |
| `W` | 문서 단 폭 / 터미널 폭 |
| `t` | 개요 보기 (`Enter` 로 그 자리로) |
| `/` `n` `N` | 검색 |
| `] [` | 쪽 넘김 · `:N` 으로 N쪽 |
| `q` | 종료 |

그림은 **반블록(`▀▄█`)이 기본**이다. 어떤 글꼴에나 있는 글자라서 옵션 없이 떠도
그림이 실제로 보인다. 점자는 해상도가 4배지만 글꼴에 없으면 네모로 보이고, 그게
기본값이면 처음 열어 본 사람이 고장으로 오해한다 — `z` 한 번으로 간다.

### 도스 시절 단축키도 받는다

HWP 는 도스에서 왔고, 그 시절 편집기의 키는 **보르랜드 IDE(터보 파스칼)와
워드스타 계보**로 널리 굳어져 있었다. 근거는 그 계보를 그대로 문서화한
[Free Pascal IDE 키 목록](https://www.freepascal.org/docs-html/user/userse32.html)
이다 — 기억으로 짐작하지 않았다.

| 키 | | 출처의 뜻 |
|---|---|---|
| `F1` `F2` `F10` | 도움 · 저장 · 메뉴 | 그대로 |
| `Alt-X` | 끝내기 | 그대로 |
| `Ctrl-Y` | 단락 지우기 | 줄 지우기 (우리 단위는 단락) |
| `Ctrl-L` | 다시 찾기 | 그대로 |
| `Ctrl-E` `Ctrl-X` `Ctrl-S` | 커서 위·아래·왼쪽 | 워드스타 다이아몬드 |
| `Ctrl-A` | 낱말 뒤로 | 그대로 |
| `Ctrl-K S Q Y L C I U` | 저장·나가기·삭제·담기·붙이기·글머리 단계 | 블록 묶음 |
| `Ctrl-Q F S D` | 찾기 · 단락 처음 · 단락 끝 | 그대로 |
| `Ctrl-Ins` `Shift-Del` `Shift-Ins` | 담기 · 잘라내기 · 붙이기 | IBM CUA |

**겹치지 않는 것은 모드 없이 그냥 받는다.** 두 벌을 외우게 하는 대신, 손이
기억하는 쪽으로 눌러도 되게 한다. 두 키 묶음은 첫 키를 누르면 아래 줄이
**무엇을 기다리는지** 말한다.

```
Ctrl-K — S 저장 · Q 나가기 · Y 단락삭제 · L 담기 · C 붙이기 · I/U 글머리 단계
```

**딱 둘이 겹친다.** 워드스타는 `Ctrl-D` 를 "글자 오른쪽", `Ctrl-F` 를 "낱말
오른쪽" 으로 쓰고 vi 는 각각 반 화면·한 화면 아래로 쓴다. 양쪽을 다 만족시킬
수 없으므로 **이 둘만** `:set keys=dos` / `:set keys=vi` 로 가른다(기본 vi).
한 화면·반 화면은 `PgDn`·`PgUp` 으로도 된다.

**없는 것은 지어내지 않았다.** `F3`(파일 열기)은 파일을 고르는 화면이 없어
비워 뒀고, `Ctrl-K B`/`K`(블록 시작·끝)도 우리에게 선택 개념이 없어 받지
않는다 — 단락이 단위다. 한글 DOS판 고유 키는 믿을 만한 출처를 못 찾아
손대지 않았다.

그리고 이 작업에 **낱말 이동**이 필요해서 같이 넣었다 — `w` `b` `e`. 한국어는
띄어쓰기가 경계다. vi 는 낱말을 "글자 묶음 / 기호 묶음 / 공백" 으로 가르는데
한글은 조사가 붙어 한 덩이로 움직이는 편이 자연스럽다 — `과업지시서를` 은 한
낱말이다. 그 바람에 `b` 에 묶여 있던 `less` 식 "한 화면 뒤로" 를 `Ctrl-B`·`PgUp`
으로 옮겼다 (vi 에서도 그쪽이 맞다).

이동·편집 키는 vi 와 같다.

```
j k        줄/단락        h l    글자        0 $     단락 처음/끝
g G        처음/끝        Ctrl-d/u  반화면    space b 화면
i a I A    끼워넣기       x      글자 삭제    dd      단락 삭제
o O        빈 단락        u      되돌리기    Ctrl-r  다시하기
yy         단락 담기      p P    붙이기 (뒤/앞) — dd 도 담는다
Tab ⇧Tab   글머리 단계 (이 문서가 쓰는 사다리를 따라간다)
:w  :wq    저장 (자가검증)              :set ime=2  두벌식 / off
ZZ  ZQ     저장하고 나가기 / 버리고 나가기  :e!  디스크에서 다시 읽기
```

#### 기능도 가져왔다 (2026-10-11)

키만 가져왔던 것을 기능까지 넓혔다. 근거는 [한컴의 단축키 일람](https://help.hancom.com/hoffice/multi/ko_kr/hwp/view/toolbar/shortcut(table).htm)
과 보르랜드 IDE 계보다 — **HWP 가 지금도 쓰는 키**다.

| 키 | | 계보 |
|---|---|---|
| `Ctrl-T` | 낱말 지우기 | 워드스타. vi 의 `dw` 자리를 이 키가 채운다 |
| `Ctrl-Q Y` | 커서에서 단락 끝까지 지우기 | 워드스타 |
| `Ctrl-K 1`~`0` | 책갈피 넣기 | 워드스타의 마크. **HWP 도 같은 키** |
| `Ctrl-Q 1`~`0` | 그 책갈피로 이동 | 같음 |
| `:marks` | 적어 둔 책갈피 보기 | — |
| `Esc` | 두 키 묶음 버리기 | 무엇을 기다리는지 말해 놓고 빠져나갈 길이 없으면 아무 키나 누른다 |

`Ctrl-T` 는 **`w` 가 가는 자리까지** 지운다. 처음엔 따로 셌고 낱말만 지우고 뒤 공백을
남겨(` 낱말 그리고 나머지`) `w` 와 다른 자리가 되었다 — 같은 일을 두 군데서 세면
반드시 어긋난다. 이제 `move_word` 를 그대로 쓴다.

책갈피는 **사라진 자리로 뛰지 않는다.** 단락을 지웠으면 그 좌표에는 다른 글이 있다 —
뛰어 놓고 "여기였나" 하게 만드는 쪽이 더 나쁘다.

#### 이때 잡은 버그 둘 — 둘 다 시험이 건너뛴 층에 있었다

**1. 도스 두 키 묶음이 실제 키로는 한 번도 동작하지 않았다.**

짝 맞추기가 `apply` 안에 있고 두 번째 키도 `Action::Operator` 로 와야 한다. vi 의
`dd`·`ZZ` 는 그 글자 자체가 `Operator` 라 맞았지만, `Ctrl-K S` 의 `s` 는 보통 모드에서
아무 데도 안 걸려 `Nothing` 이 되었다. 실측: `Ctrl-K S` 가 저장하지 않고, `Ctrl-Q S` 가
커서를 옮기지 않고, **`Ctrl-K z` 는 그림 보기 방식을 돌렸다.**

시험은 `apply(Operator('\u{1}'))` + `apply(Operator('s'))` 를 직접 불러서 통과했다 —
**버그가 사는 층을 건너뛴 시험**이다. 이제 두 번째 키는 `step` 이 글자 그대로 받고,
시험도 실제 키로 넣는다. 묶음에 없는 키는 삼키지 않고 말한다.

**2. 고치기 모드에서 큰 이동이 전부 죽어 있었다.**

`g` `G` `Ctrl-F` `Ctrl-B` `Ctrl-D` `]` `[` — 전부. 그 동작들이 보기(`app.top`)만
옮기는데, 한 걸음 뒤에 `reveal_cursor` 가 커서 쪽으로 보기를 되돌려 **아무 일도
일어나지 않았다.** 읽기 전용에서는 멀쩡했으므로 고치기 모드만 그랬고, 65단락 문서를
`j`/`k` 로만 다닐 수 있었다.

고친 뒤: `G`→단락64, `Ctrl-F`→단락15, `]]`→단락36. **단락 수가 아니라 그려진 줄 수로
센다** — 한 단락이 여러 줄로 접히므로 단락으로 세면 한 화면이 아니라 열 화면을 뛴다.

이것도 시험이 없던 자리다. `apply` 를 직접 부르는 시험은 `app.top` 이 움직이는 것을
보고 통과한다 — `reveal_cursor` 는 `step` 에 있다.

#### F2 는 두 계보가 다르다

보르랜드는 `F2` = 저장, HWP 는 `F2` = 찾기다. **먼저 적어 둔 쪽(저장)을 지킨다** —
이미 쓰고 있는 키를 바꾸는 쪽이 더 나쁘다. 찾기는 `/`·`Ctrl-Q F`·`Ctrl-L`(다시 찾기,
HWP 와 같은 키)로 열려 있다.

### 파이프·스크립트용 명령

기본 목록에서는 **숨겼다.** 사람이 외울 명령은 `view`·`edit` 둘이고, 나머지는
스크립트가 부르는 것이다. `hwp help <명령>` 으로 본다.

```
hwp page <파일> [--only N]            # 같은 화면 모델을 글로
hwp json <파일> [--profile P]         # LLM 용 단일 JSON 객체
hwp toc <파일>                        # 개요 트리 + 이 문서의 글머리 단계 사다리
hwp img <파일> [--dots N]             # 그림 목록 / 글자로 그리기
hwp cells <파일> [--table N]          # 표를 격자로 (셀 좌표 확인)
hwp set-cell <파일> 표:행:열=값 …     # 서식 채우기 (자가검증 저장)
hwp set-para <파일> 구역:단락=값 …    # 본문 단락 글자 바꾸기
hwp para <파일> --insert/--delete …   # 단락 넣기·빼기
hwp witness <파일> [--text] [--style] # 독립 증인으로 구조·문단서식 세기
hwp doctor                            # 백엔드가 고정대로 붙어 있는지 진단
hwp view <파일> --frame 100x30        # 띄우지 않고 한 프레임만 글로
```

### 밖에서 가져온 문서로 시험했다

회귀 코퍼스(`samples/`, 실무 문서 14개) 밖의 공개 문서로 돌려 봤다. 받은 곳은
[neolord0/hwplib](https://github.com/neolord0/hwplib) 의 `sample_hwp/` 와
[hahnlee/hwp-rs](https://github.com/hahnlee/hwp-rs) 의 시험 자료다.

| 문서 | 크기 | 결과 |
|---|---|---|
| `한글문서파일형식_5.0_revision1.3.hwp` | 336 KB · 70쪽 · 619단락 · 구역 6 | **버그 3개** 발견 |
| `big_file.hwp` | 10.6 MB · **16,384쪽** · 147,456단락 | 백엔드 한계 확인 |
| `annual_report.hwp` | 2.2 MB · 글상자 240단락 | 못 그리는 것이 있다 |
| `ole.hwp` | 236 KB · OLE 개체 | 열린다 |

#### 1. 배포용 문서를 조용히 빈 문서로 보여줬다

한글문서파일형식 스펙 문서는 **배포용**(`FileHeader` 속성 bit 2)이다. 본문이
`BodyText/` 가 아니라 `ViewText/Section0~5` 에 구역별로 암호화되어 있고,
`BodyText/Section0` 에는 337바이트 껍데기만 남는다.

그래서 읽으면 **오류 없이 1단락**이 나왔다. 백엔드는 70쪽 619단락이라고 하는데
화면에는 "70쪽" 이라고 적힌 **빈 쪽**이 떴다. 조용히 틀리는 쪽이라 제일 나쁘다.

지금은 열기 전에 가려내고 길을 알려준다.

```
$ hwp 한글문서파일형식_5.0.hwp
Error: … 는 **배포용** 문서다 — 본문이 ViewText 에 암호화되어 있어 그대로는
  읽을 수 없다.
  편집 가능한 형태로 먼저 바꿔라:
    rhwp convert … 바꾼이름.hwp
```

그 조언이 되는지 확인했다 — 변환하면 619단락이 나오고(백엔드 수치와 일치)
70쪽이 다 읽힌다. 암호 걸린 문서(bit 1)도 같이 가려낸다.

#### 2. 줄 세그먼트가 없는 단락에서 문서 전체가 안 열렸다

`dump-pages` 의 `lineSegs` 를 `count`·`first`·`last` 필수로 받고 있었는데, 이
문서는 650항목 중 **96개**가 `count` 만 준다. `missing field 'first'` 로
조판값을 하나도 못 받아 **문서가 열리지 않았다.** 화면 몇 줄이 덜 정확한 것과
문서를 못 보는 것은 다른 일이다 — 이제 없으면 단락 전체 줄 수로 떨어진다.

#### 3. 셀 안의 탭이 표를 깼다

`unicode-width` 는 탭에 `None` 을 주고 우리는 그걸 0 으로 받았는데, 터미널은
탭을 다음 탭 스톱(보통 8칸)까지 띄운다. 탭이 든 줄이 **109개**였고 표 테두리가
어긋났다.

세는 쪽과 그리는 쪽을 **1글자 = 1칸 = 공백 하나**로 맞췄다. 글 모형에는 탭을
그대로 둔다 — 커서 오프셋이 글자 수로 계산되고, 백엔드의 `--offset` 도 탭을 한
글자로 센다. 고친 뒤 이 문서의 **표 171개가 전부 줄 폭이 고르다.**

#### 4. 증인이 찍는 번호가 편집 좌표가 아니었다

`hwp witness --text` 가 목록 순번(`[ 12]`)을 찍었는데 그건 구역을 가로질러 센
수다. 구역이 6개인 이 문서에서 그 번호를 `set-para 0:12` 에 넣으면 "없는
단락이다" 가 나온다. **찍는 번호가 곧 쓰는 번호여야 한다** — 이제 `1:12` 처럼
좌표를 그대로 찍는다. (이 프로젝트가 같은 실수를 두 번 한 자리라서, 코퍼스
시험으로 구조를 못 박았다.)

그 좌표로 619단락·6구역 문서를 고치고 자가검증 저장까지 **0.42초**에 통과했다.

#### 백엔드의 한계 — 16,384쪽

`big_file.hwp` 는 실측으로:

| 단계 | 시간 | 메모리 | 산출 |
|---|---|---|---|
| 우리 증인(파일 읽기) | **0.37초** | 133 MB | 147,456단락 |
| 백엔드 `info` | 62초 | 457 MB | — |
| 백엔드 `dump-pages` | 98초 | **2.1 GB** | JSON **105 MB** |

화면을 그리려면 조판값이 필요하니 이 비용은 피할 수 없다. 말없이 기다리게 두지
않으려고, 1MB 넘는 문서는 열기 전에 stderr 로 조판 중임을 알린다. 쪽 단위로
조판값을 받는 길이 있으면 그게 답인데 백엔드에 아직 없다.

#### 못 그리는 것 — 글상자

`annual_report.hwp` 는 9쪽인데 본문 단락이 10개뿐이고 **240단락이 글상자 안**에
있다. 표는 그리지만 글상자는 아직 안 그려서, 이 문서는 `◻`(그리지 못한 개체)만
보이는 쪽이 된다. 적어도 **있다는 사실은 숨기지 않는다.**

우리 코퍼스에서는 글상자 단락이 드물다(1,400단락 중 50). 이 문서처럼 전체가
글상자인 보고서는 따로 손봐야 한다.

### 표 열 폭은 문서가 정한다 — 내용이 아니라

2026-10-12 보고: "실제 문서의 표 크기와 상동하지 않는다." 맞았다. 열 폭을 **내용
길이로 짐작**하고 있었다 — 긴 글이 든 열이 넓어지므로 문서가 20:80 으로 적어 둔 2열
표가 거꾸로 그려졌다.

```
s02.hwp 표20 — 문서 [9166, 38546] = 19:81
   전: 내용으로 짐작 → 거꾸로 (71.7%p 차이)
   후: 문서가 적어 둔 폭 → 14:61 = 19:81
```

**조판값은 표의 전체 폭만 준다.** `dump-pages` 의 `table.widthPx` 가 그것이고 열별
폭은 없다. 그래서 **증인이 셀 레코드에서 직접 읽는다** — HWP5 는 `LIST_HEADER`
payload 의 16·20바이트(폭·높이, HWPUNIT), OWPML 은 `hp:cellSz` 다.

바이트 자리를 맞게 짚었는지는 **조판값과 대조해 확인했다**: s16.hwp 표1 이
`4836 + 565 + 42758 = 48159` 이고 조판값이 `642.12px × 75 = 48159` — 정확히 같다.
코퍼스 123개가 1px 오차 안에서 맞는다. 자리를 한 바이트 밀면 그 합이 흐트러지고
시험이 잡는다(되돌려 확인했다).

전수 측정(표 126개) — 열 비율 차이 중 가장 큰 것의 평균:

| | 평균 | 최악 |
|---|---|---|
| 내용으로 짐작 | **16.35%p** | 71.7%p (2열 표가 거꾸로) |
| 문서가 적어 둔 폭 | **1.77%p** | 21.2%p (9열, 바닥에 걸림) |

남은 차이는 거의 **바닥(`MIN_CELL` 4칸)** 때문이다. 문서의 2% 짜리 열을 비율대로
주면 한 칸이 되어 글자를 읽을 수 없다. 그래서 바닥을 지키고 **비율이 거기서 깨지는
것은 터미널의 한계로 받아들인다** — 어긋난 표보다 읽히는 표가 낫다는, 선 문자를
ASCII 로 바꿀 때와 같은 판단이다. 시험은 바닥에 걸린 표를 세지 않는다.

조판값의 `table` 칸(`colCount`·`widthPx`·`heightPx`)도 그동안 **읽고 버리고**
있었다. 이제 받는다.

### 표는 선이 아니라 커서로 읽는다 — `T`

칸 이동은 **세 벌을 다 받는다.**

| | |
|---|---|
| `←` `↓` `↑` `→` | 가장 손이 간다. 전부터 됐는데 **아무도 알려 주지 않았다** |
| `w` `a` `s` `d` | 게임 쪽 관례. 칸을 고르는 일은 vi 보다 그쪽에 가깝다 |
| `h` `j` `k` `l` | vi |

표 모드는 분기가 먼저 돌아서 본문의 `a`(넣기)·`d`(지우기)·`w`(낱말 앞)와 **부딪히지
않는다** — 네 자리가 비어 있었다. 본문에서는 그대로다. 메뉴도 같은 세 벌을 받는다
(`ws` 항목, `ad` 묶음).

#### 표 만들기 — `:table 3x4`

커서가 있는 단락에 빈 표를 만든다. 메뉴(`m` → 넣기)에도 있다.

```
구역0 단락12 에 3×4 표를 만들었다 (표0) — T 로 들어간다
```

**백엔드는 표와 함께 단락 하나를 넣고, 그 자리부터의 표 번호를 +1 한다.** 실측
(s16.hwp 단락3 에 2×2 를 넣었다):

```
전:  t0 단락0   t1 단락0   t2 단락0   t3 단락5   t4 단락5   t5 단락12
후:  t0 단락0   t1 단락0   t2 단락0   t3 단락3(새)  t4 단락6  t5 단락6  t6 단락13
```

그래서 `Op::InsertTable` 은 **새 표가 받을 번호를 미리 세어 적는다**(`index`). 그
번호는 백엔드에 보내지 않는다 — "이렇게 되어야 한다" 를 만드는 데만 쓰고, 저장 뒤
증인과 대조한다. **잘못 세면 저장이 멈춘다**:

```
멈췄다: 저장을 멈췄습니다 — 저장본이 기대와 다릅니다. 원본은 그대로 두었습니다.
          표0 (0,0) 의 글자가 다르다
            기대: (빈 칸)
            실제: 신청 자격의 적정성 확인서
파일이 남았나: false
```

진단도 **밀린 것과 생긴 것을 가른다.** 단락에서 했던 것과 같은 정렬을 표에도 한다 —
안 하면 "표3 의 (0,0) 이 '신청 자격의 적정성 확인서' 에서 '' 로 바뀌었다" 가 되는데,
실제로는 그 표가 표4 로 옮겨 간 것뿐이다. 처음에 그렇게 나왔다.

```json
"changed": [
  {"kind":"para",  "change":"added", "at":"0:3"},
  {"kind":"table", "change":"added", "table":3, "rows":2, "cols":2}
]
```

화면에서는 **쌓인 편집이 있으면 거절한다**(`먼저 저장하라`). 표가 들어가면 뒤쪽 단락
좌표가 밀리는데 쌓아 둔 연산은 밀리기 **전**의 좌표로 적혀 있다 — 섞으면 어느 쪽이
먼저인지에 따라 엉뚱한 단락을 고친다. 만든 뒤에는 디스크에서 다시 읽는다. 표가
들어가면 쪽 경계와 줄 수가 달라지고 그건 조판기가 하는 일이다 — 흉내 내면 화면과
문서가 어긋난다.

만들고 바로 채우는 흐름이 한 줄로 간다: `:table 3x4` → `T` → `i` 항목 → `Esc` →
`d` → `i` 값 → `Esc` → `:w`.

#### 백엔드는 우리가 쓰는 것보다 훨씬 많다

`rhwp edit` 의 하위명령을 세어 보니 **마흔 가지가 넘는다.** 우리가 쓰는 것은 여섯이다.
쓰지 않고 있던 것 중 눈에 띄는 것:

`replace-text`(일괄 치환) · `insert-row`/`insert-col`/`delete-row`/`delete-col` ·
`merge-cells`/`split-cell` · `split-table`/`merge-table` · `set-column-widths` ·
`insert-page-break` · `insert-footnote`/`insert-endnote` · 머리말·꼬리말 ·
`insert-image`(도장·서명) · `redact`(개인정보 마스킹) · `sanitize`(메타데이터 제거)

표 만들기를 붙이면서 알았다. 하나씩 올릴 때마다 **자가검증이 그 연산의 결과를 예측할
수 있어야** 하므로(표 번호 밀림이 그 예다) 한꺼번에 열지 않는다.

#### 칸을 고치는 것은 `i` (또는 `↵`) — **커서가 칸 안에 선다**

```
표0 2행1열 안  ·  Esc 로 끝낸다
      │   사업명« »   │     ← i 로 들어가면 글자 끝
      │   사업«명»    │     ← ←
      │   사«업»명    │     ← ←
      │  사업명한글« » │     ← 두벌식으로 한 키씩 (ㅎ 하 한 → 한글)
```

커서가 **글자 하나를 정확히 짚는다.** 한글은 두 칸이라 한 칸만 뒤집으려 하면 글자를
반만 집을 수 없어서 빈칸이 끼어들고 뒷글자가 한 칸 밀린다 — 처음에 그렇게 나왔다
(`사`[빈칸 반전]`업명`). 그래서 글자의 폭만큼 집는다.

**접고 정렬하는 일은 한 함수(`grid::lay_cell`)가 한다** — 그리는 쪽과 커서를 놓는
쪽이 같아야 커서가 글자 위에 선다. 따로 세면 접는 자리나 정렬 여백이 한 칸 어긋나고,
그러면 커서가 글자 사이에 떠서 "어디를 고치는지" 를 알 수 없다.

**끼워넣기 모드를 그대로 쓴다.** 두벌식 조합·지우기·커서 이동을 베끼지 않으려면
그래야 한다 — 베끼면 반드시 한쪽만 고쳐지는 날이 온다. 다른 것은 `Esc` 가 본문이
아니라 **표로** 돌아가는 것뿐이다(본문으로 튀어나오면 방금 고친 칸을 다시 찾아야 한다).

그 대가로 `Enter`(빈 단락 열기)와 `↑↓`(단락 이동)가 같이 들어온다. 칸을 고치다 Enter 를
누르면 **본문에 빈 단락이 생기는데**, 사람은 "칸 입력을 끝냈다" 고 생각한 순간이다.
그래서 Enter 는 끝내는 것으로 받고, 세로 이동은 거절하며 왜인지 말한다.

**한 번의 고치기가 연산 하나다.** 글자마다 `SetCell` 을 쌓으면 저장 때 같은 칸에 열
번 쓰고 되돌리기도 글자 단위가 된다. `u` 로 한 번에 처음으로 돌아가고 `Ctrl-R` 로 다시
하며, 저장은 평소대로 `:w` 가 자가검증을 걸어서 한다.

조합 중인 자모는 **화면에만** 보인다 — 확정 전 글자를 담아 두면 저장될 수 있다.

`:cell <글자>` 는 그대로 남겼다. 칸을 열지 않고 바로 쓰는 길이고, 무엇을 덮었는지
(`"사업명" → "과업명칭"`) 말해 준다.

**여러 단락이 든 칸은 거절한다.** 줄바꿈을 공백으로 바꿔 넣으면 조용히 문서를
망치므로, 그 경우는 `hwp set-cell 표:행:열=…` 를 쓰라고 말한다.

칸 편집을 **버퍼**가 들고 있다(`Buffer.cells`). 바깥(`ScreenDoc`)에만 두면 `u` 가 칸을
못 되돌린다 — 되돌리기 기록이 버퍼에 있기 때문이다.

2026-10-10 까지 **칸을 넘나들 수는 있는데 고칠 길이 아예 없었다.** "들어가면 그게
그대로 `set-cell` 의 좌표다" 라고 적어 두고, 그 좌표로 고치는 것은 명령줄로 나가야
했다.

선으로만 보여주면 "지금 어느 칸인지" 를 사람이 눈으로 따라가야 하고, 선 문자는
터미널마다 폭이 달라 **그 눈마저 못 믿는다.** 그래서 표 안으로 들어가 칸을
커서로 쥔다.

```
T          커서가 있는 단락의 표로 들어간다 (없으면 뒤쪽에서 가장 가까운 표)
hjkl ←↑↓→  칸 이동        Tab ⇧Tab  다음·앞 칸
T          다음 표로      Esc q     나가기
```

들어가면 **지금 칸이 뒤집혀** 보이고 상태줄이 이렇게 말한다.

```
  [hwp5]  표3 2행1열  ·  Tab 다음칸 · Esc 나가기
  칸 · 농림축산식품부
```

그 좌표가 **그대로 `hwp set-cell` 의 좌표**다(`표번호:행:열`). 화면이 가리키는
자리와 고치는 자리가 하나다 — 비대화형으로 쓰려면 그 수를 그대로 옮기면 된다.

상태줄 아래 줄은 그 칸의 **실제 글자**다. 칸이 좁아 글자가 접혀 보일 때 무엇이
들었는지는 이것뿐이다 (스프레드시트의 수식 줄과 같은 몫).

**병합된 칸을 두 번 세지 않는다.** 좌표를 하나씩 더해 가며 실제로 존재하는
칸(그 칸의 좌상단)만 찾으므로, 병합 안쪽 좌표는 지나친다. 행 전체를 병합한
제목 칸에서 오른쪽으로 갈 곳이 없는 것도 맞는 동작이다.

아직 **칸 안의 글자를 화면에서 고치는 것은 안 된다** — 커서가 칸을 쥐는 것까지
했다. 고치려면 그 좌표로 `hwp set-cell` 을 쓴다(자가검증 저장을 탄다).

### 표가 어긋나는 원인은 터미널의 Ambiguous 폭이다

표의 끝선이 안 맞는다면 **거의 이것이다.** 한글 크기 때문이 아니다 — 한글은
유니코드가 `W`(2칸)로 못 박아 두었고 모든 터미널이 2칸으로 그린다.

문제는 **표를 그리는 선 문자 `─ │ ┼ ├ ┤ ┬ ┴ ┌ ┐ └ ┘` 가 전부 East Asian
Ambiguous** 라는 점이다. 유니코드가 1칸인지 2칸인지 정하지 않고 **터미널이
정한다.** 코퍼스를 찍은 줄의 **76%** 에 Ambiguous 글자가 있고, 54,754개 중
**53,000개가 선 문자**다.

```
터미널이 1칸으로 볼 때   ┌────┬────┐ 11칸 · │가나│다라│ 11칸  → 맞는다
터미널이 2칸으로 볼 때   ┌────┬────┐ 22칸 · │가나│다라│ 14칸  → 8칸 어긋난다
```

글자 쪽도 같다: `Ⅰ. 사업추진 방향` 16↔17칸, `① 첫째 · 둘째` 13↔15칸,
`※ 참고` 6↔7칸. `· • × 「 」 → ≤ ○` 가 모두 Ambiguous 다.

#### 세 가지로 해결한다

**1. 띄울 때 터미널에 직접 물어본다.** 코드로는 알 수 없는 값이므로 묻는다 —
커서를 맨 왼쪽으로 옮겨 `─` 를 찍고 `ESC [ 6 n`(Device Status Report)로 위치를
받아 1칸인지 2칸인지 센다. 150ms 만 기다리고, 대답이 없으면 좁은 쪽으로 둔다.

**2. 사람이 덮을 수 있다.** 화면에서 `:set amb=wide` / `:set amb=narrow`,
비대화형에서는 `HWP_AMBIGUOUS=wide hwp page …`.

**3. `hwp doctor` 가 자를 찍는다.** 눈으로 바로 확인할 수 있다.

```
  터미널 폭 자가확인 — 아래 두 줄의 **오른쪽 끝이 맞는지** 보세요
    ┌────┬────┐
    │가나│다라│
    └────┴────┘
    어긋나면 `HWP_AMBIGUOUS=wide hwp …` 또는 화면에서 `:set amb=wide`.
```

#### 넓은 터미널에서는 표를 ASCII 로 그린다

**유니코드에 "좁다고 보장된" 선 문자가 없다.** `+ - | =` 만 ASCII 라서
확실하다. 그래서 Ambiguous 를 2칸으로 그리는 터미널에서는 ASCII 로 간다 —
모양을 잃는 대신 격자가 맞는다. 어긋난 예쁜 표보다 맞는 표가 읽힌다.

```
+==============+========================================+
|    기 관     |          조사 분야(주요 내용)          |
+--------------+----------------------------------------+
|농림축산식품부|ㅇ (산업화 분야) AI·디지털 전환,        |
```

바깥 테두리는 `+===+`, 안쪽 선은 `+---+` 로 구분한다. 둘 다 `+---+` 면 표가
어디서 끝나는지 사람도 기계도 알 수 없다.

#### 표만이 아니었다 — 장식 전부가 같은 규칙을 받는다

위 결정을 **표만 받았다.** 도움 보기·메뉴의 테두리는 유니코드 그대로였고,
안내줄의 `· → ↓ —` 와 그림의 반블록 `▀▄█`·점자도 그대로였다. 전부 Ambiguous 다.

이게 안 보였던 이유: 이 프로그램은 폭을 `wrap::char_width` 로 재는데 **ratatui 는
언제나 좁은 폭(Ambiguous = 1)으로 잰다.** 우리 계산은 맞고 배치만 어긋나므로
코드를 읽어서는 드러나지 않는다. 가로세로로 찍어 **줄 폭을 재서야** 보였다 —
문서 6 × 크기 7 × 키 12 × 폭정책 2 = 23,040줄 중 **1,070줄이 넘쳤다.**

```
             넓은 정책, 고치기 전                 고친 뒤
   │ 저장                       │        | 저장                       |
   │ 저장하고 나가기            │        | 저장하고 나가기            |
   └───────────┘  ← 상자가 깨진다        +----------------------------+
```

그래서 규칙을 하나로 모았다:

> 우리가 **고른** 장식 글자는 넓은 정책에서 ASCII 로 바꾼다
> (`wrap::narrow`, 폭 1칸이 보장된 글자로, **글자 수를 유지해서**).
> **문서가 준 글자는 바꾸지 않는다.**

두 번째 문장이 중요하다. 공문서는 `AI·디지털` 처럼 가운뎃점을 구분자로 쓰는데
`.` 으로 바꾸면 `AI.디지털` 이 되어 **문서를 잘못 보여 주는** 셈이다. 장식을
고르는 것과 문서를 고쳐 보여 주는 것은 다른 일이다. 그래서 고친 뒤에도 넘치는
줄이 23,040줄 중 **7개** 남아 있다 — 전부 문서 본문의 `–`(en dash)와 `‘`(여는
인용표)다. **남겨 둔 것이다.**

그림은 ASCII(`#`)로 간다. 반블록을 반 폭으로 줄여 그리는 길도 있지만 ratatui 가
그걸 1칸으로 셈하므로 배치가 또 어긋난다 — 선 문자와 같은 결론이다.

시험이 이제 두 가지를 본다. 선 문자는 **어디에도** 없어야 하고(문서 글자에는
나오지 않는다), 머리글·상태줄·도움줄은 Ambiguous 를 **하나도** 쓰지 않아야 한다
(그 세 줄에는 본문이 오지 않으므로 전부 우리가 고른 글자다). 이 시험을 켜자마자
`—`(em dash)를 두 군데서 더 찾았다 — 도움 보기 제목과 상태줄의 단 폭 설명이었고,
넓은 정책에서 뒤의 공백 한 칸을 먹고 있었다(`도움 —? 또는 …`).

#### 이 과정에서 잡은 버그

**`wrap` 이 폭 정책을 안 따랐다.** "폭을 재는 곳은 전부 한 함수를 지나야
한다" 고 적어 두고 `wrap` 자신이 `unicode-width` 를 직접 불렀다. 접는 폭만
좁은 기준이고 그리는 칸은 넓은 기준이라, s03.hwpx 에서
`• 1,000,000원×25명(25,000` 이 27칸인데 20칸 칸에 그대로 들어가 **옆 칸의
`│` 를 지웠다.**

코퍼스 시험이 이제 **두 정책 양쪽에서** 표 252개의 줄 폭을 전수로 본다.
넓은 쪽에서 아무것도 검사하지 않고 통과하던 구멍이 있었는데(ASCII 에서 바깥
테두리와 안쪽 선이 구분되지 않아 표의 끝을 못 찾았다), 테두리를 `+===+` 로
구분하면서 같이 막혔다.

#### 아직 못 하는 것 — 조합용 옛 한글

`ᄒᆞᆫ글`(U+1112 U+119E U+11AB) 처럼 **조합용 자모로 적힌 옛 한글**은 글꼴이
합쳐 그리면 2칸, 못 합치면 자모 셋이 각각 보인다. `unicode-width` 는 합쳐지는
쪽을 가정해 2칸으로 세므로, 합치지 못하는 글꼴에서는 그 줄만 넓어진다.
정규화(NFC)로도 안 된다 — `ᆞ`(아래아)에는 현대 한글 음절이 없다. 코퍼스에서는
한컴 로고 표기에만 나온다.

### 글자 꾸밈 — 본문은 그린다, 표 칸은 아직

진하게·기울임·밑줄·취소선을 **읽어서 터미널 꾸밈으로 그린다**(ANSI SGR
1·3·4·9). 어느 글자가 꾸며졌는지는 `hwp witness <파일> --deco` 로 본다.

```
$ hwp witness 과업지시서.hwp --deco
글자 꾸밈 — B 진하게 · I 기울임 · U 밑줄 · S 취소선
  0:2
     B      0+6   "1. 과업명"
  0:5
     B      0+7   "2. 과업목표"
```

**쓰임** — 코퍼스 run 4,235개 중 진하게 957(23%) · 기울임 203(5%) ·
밑줄 47(1%) · 취소선 0.

#### 읽는 자리 (실측)

HWP5 `DocInfo` 의 `CHAR_SHAPE`(`HWPTAG_BEGIN + 5`), payload **74바이트**,
속성 `UINT32` 가 **오프셋 46**:

| 비트 | 뜻 | 확인 |
|---|---|---|
| 0 | 기울임 | 코퍼스 6문서에서 변환본 HWPX 의 `hh:italic` 과 전수 일치 |
| 1 | 진하게 | 같음 |
| 2 | 밑줄 | 같음 |
| **19** | **취소선** | **만들어서** 확인 — 그 속성만 켠 HWPX 를 `rhwp convert` 로 되돌렸다 |

(덤으로 8 외곽선, 11 그림자 — 터미널에 옮길 것이 없어 담지 않는다.)

구간은 `PARA_CHAR_SHAPE`(+52)의 `(위치, 글자서식번호)` 쌍이다. **위치는 원시
`PARA_TEXT` 의 wchar 기준**이고 컨트롤이 8 wchar 를 차지한다 — 실측: 보이는
글자가 13개인 단락의 구간 위치가 **20** 이다(보이는 글자 기준으로는 나올 수
없는 수다). 읽을 때 보이는 글자 기준으로 옮겨 둔다.

HWPX 는 `hp:run@charPrIDRef` + `header.xml` 의 `hh:charPr` 다. **`hh:underline`
·`hh:strikeout`·`hh:shadow` 는 값이 `NONE` 이어도 엘리먼트가 늘 있다** — 있는지만
보면 전부 켜진 것으로 읽힌다(처음에 그렇게 재서 그림자가 100% 로 나왔다).
`hh:bold`·`hh:italic` 은 반대로 참일 때만 나온다.

#### 두 길로 읽어 맞춰 본다

같은 문서를 HWP5 로, `rhwp export-hwpx` 로 바꾼 HWPX 로 읽어 **어느 보이는
글자가 꾸며졌는지** 대조한다. 코퍼스 시험이 매번 돈다. 그 과정에 나온 것들:

- **빈 단락은 `PARA_TEXT` 를 아예 안 내면서 `PARA_CHAR_SHAPE` 는 낸다**
  (s13.hwp 단락1). 위치표를 단락마다 비우지 않으면 앞 단락 표를 물려받아 빈
  단락에 11자 구간이 붙는다.
- **HWPX 는 글꼴이 달라지면 `hp:run` 을 쪼갠다.** 꾸밈이 같아도 구간이 둘이
  된다(`B 0+4`,`B 4+30` vs `B 0+34`). 붙은 것끼리 합친다.
- **컨트롤 한 글자에 붙은 꾸밈**이 있다(그림 하나에 진하게). 글자가 아니므로
  버린다.
- 남은 차이는 **컨트롤을 구간에 넣는지**뿐이어서(115단락 중 3), 비교에서 뺀다.
  화면에 차이가 없다.

#### 표 칸은 안 그린다 (일부러 미뤘다)

본문은 그리는데 **표 칸·글상자 안은 꾸밈 없이 그린다.** 격자가 글자 줄
(`Vec<String>`)을 내놓는 구조라, 칸마다 꾸밈 구간을 들고 Span 으로 쪼개는
층이 하나 더 필요하다.

그리고 실측해 보니 **기울임은 본문에 0개이고 101개가 전부 표·글상자 안**이다
(s00: 본문 0 / 칸 101, s14: 0 / 50, s15: 0 / 36). 그래서 지금 화면에서 기울임을
볼 수 없는 것은 읽기 버그가 아니라 이 공백이다.

**우선순위를 낮게 두기로 했다** — 표의 모양(테두리·병합·가운데 정렬)은 이미
나오고, 칸 안 글자가 진하게인지는 공문서를 읽는 데 거의 영향이 없다. 할 일로만
남겨 뒀다.

#### 쓰는 길은 재 뒀고, 아직 내보내지 않는다

백엔드 `edit apply-char-format --props JSON --offset N --count N`:

| 넣은 값 | |
|---|---|
| `{"bold":true}` `{"italic":true}` `{"underline":true}` | ✓ |
| `{"strikethrough":true}` | ✓ (비트 19) |
| `{"strikeout":true}` · `{"strikeOut":true}` · `{"cancel":true}` | **아무 말 없이 무시** |

취소선 키는 `strikeout` 이 아니라 **`strikethrough`** 다.

내보내지 않는 이유는 따로 있다. **자가검증 저장은 글자와 구조만 대조하고
글자서식 번호는 보지 않는다.** 지금 꾸밈 쓰기를 내면 검증되지 않은 쓰기 경로가
된다 — 누름틀 `fill` 을 미룬 것과 같은 이유다. 이제 증인이 꾸밈을 읽으니
그걸 저장 검증에 넣는 일이 선행이다.

### 다른 이름으로 저장 — 둘이 다르다

| | |
|---|---|
| `:saveas <경로>` | 쓰고 **그 뒤로 새 이름을 고친다**. 머리글이 바뀌고 `:w`·`:e!` 도 그쪽으로 간다 |
| `:w <경로>` | 사본만 떨어뜨린다. **고치는 것은 여전히 원본**이라 "편집 N건" 표시가 남아 있다 |

vi 와 같은 가름이고, 여기서는 그 차이가 **글자 그대로 사실**이다 — `:w <경로>` 뒤에
원본은 아직 저장되지 않았으므로 `q` 가 계속 거부한다. 거기서 `mark_saved` 를 하면
`q` 가 편집을 말없이 버린다.

**있는 파일은 덮지 않는다.** `:saveas! <경로>` / `:w! <경로>` 로 말해야 덮고, 거부할
때 **그 명령을 적어 준다** — "덮어쓰기 옵션을 쓰라" 는 쓸모가 없다.

고친 것이 없어도 사본은 나온다. 처음엔 저장 경로가 "저장할 편집이 없다" 로 거부해서
**파일이 안 생겼는데**, 그건 제자리 저장에 맞는 말이고 "이 문서를 다른 이름으로" 라는
부탁에는 틀렸다. 바이트가 같으므로 검증할 것도 없다.

확장자는 원본과 같아야 한다(「기계 쪽 입구」의 같은 절). 사람 쪽과 기계 쪽이
**같은 함수**(`edit::check_same_format`)를 쓴다 — 둘에 따로 적으면 한쪽이 빠지고,
빠진 쪽이 조용히 변환을 통과시킨다.

메뉴(`m`)의 **파일** 묶음에도 있다. 경로를 받아야 하므로 고르면 명령줄이 `:saveas `
까지 **채워져** 뜬다 — `Action` 에 경로를 실어 보낼 수 없으니 사람에게 묻는다.

#### 파리티는 한 방향만 지켜지고 있었다

`api::capability_of` 는 **사람 쪽 동작마다 기계 쪽 길을 적게** 강제한다(빠짐없는
`match`). 그 반대는 강제하지 않는다 — 그래서 기계 쪽에만 있던 `output`(다른 이름으로
쓰기)이 사람 쪽에 없는 것을 아무도 잡지 못했다. 사용자가 물어서 알았다.

`:` 명령은 키 쓸기로 찾을 수 없어서(`:` 는 명령줄을 여는 키일 뿐이다) 할 수 있는 일
목록에 **손으로** 적는다. 손으로 적은 목록은 어긋나므로, 시험이 적힌 명령을 `run_ex`
에 넣어 보고 "모르는 명령" 이 나오는지 확인한다.

### 나가기는 vi 를 따른다 — 특히 `!` 의 뜻

| | |
|---|---|
| `q` · `:q` | 나간다. **저장 안 한 편집이 있으면 거부한다** |
| `:q!` · `ZQ` | 버리고 나간다 |
| `ZZ` · `:wq` · `:x` | 저장하고 나간다 (저장이 멈추면 **나가지 않는다**) |
| `:e` | 디스크에서 다시 읽는다 — 편집이 있으면 거부 |
| `:e!` | 버리고 다시 읽는다 |
| `Esc` | **끝내지 않는다** — 보통 모드로 돌아갈 뿐이다 |

전에는 `q`·`Esc`·`:q` 가 **전부 그냥 끝냈다.** 친 글이 말없이 사라지는
쪽이었고, 특히 보통 모드의 `Esc` 가 종료였던 탓에 습관적으로 누르면 편집이
날아갔다. vi 가 `:q` 에 `E37: No write since last change` 를 내고 `:q!` 를
요구하는 데는 이유가 있다.

`!` 는 **"그래도 하라"** 다. 버리는 일은 사용자가 명시적으로 말해야 한다.
`ZZ` 는 저장이 멈추면 나가지 않는다 — 자가검증이 거부했는데 화면을 닫으면
무엇이 어긋났는지 읽을 기회가 사라진다.

`ZQ` 처럼 짝이 되는 키도 받는다. `Z` 뒤에 엉뚱한 키가 오면 **삼키지 않고**
그 키로 다시 기다린다(vi 와 같다).

### 되돌리기는 지운 것도 되살린다

전에는 `dd` 뒤 `u` 가 **"되돌릴 수 없다"** 고 답했다. 이유는 재생 로그에 지운
내용이 없다는 것이었는데(`delete-text --count 3`), 그건 **로그의 성질이지
되돌리기의 한계가 아니다.** 일을 잃는 쪽이었다.

둘을 분리했다.

| | 무엇인가 | 들고 있는 것 |
|---|---|---|
| `EditLog` | `:w` 에서 rhwp 에 **재생할 명령** | 좌표와 개수 (rhwp 가 받는 그대로) |
| 되돌리기 기록 | 버퍼를 **이전 상태로 돌리는 법** | 지운 **글자**까지 |

같은 길이로 같이 쌓고 한 칸씩 같이 꺼낸다. 어긋나면 로그를 되돌려 놓고
멈춘다 — 짐작으로 버퍼를 건드리지 않는다.

그 기록이 **담아 두는 자리(register)도 겸한다.** vi 처럼 `dd` 가 지우면서
담으므로 `dd` → `p` 로 단락을 옮길 수 있고, `yy` 는 담기만 한다. 붙이기는
단락 단위다 — 이 편집기의 좌표가 단락이고, `insert-paragraph` 는 백엔드에
이미 있는 검증된 연산이라 그 길을 그대로 탄다.

`Ctrl-r` 다시하기는 **재생 로그의 `Op` 로** 앞으로 간다. 되돌리기 기록을
뒤집으려다 막혔다 — "넣은 글자를 뺀다" 를 뒤집으면 그 글자가 필요한데 거기엔
개수만 있다. 글자는 `Op::InsertText` 가 들고 있다(rhwp 에 보낼 내용이니까).

새로 고치면 다시하기 줄을 버린다. 안 버리면 갈라진 역사를 다시 하게 되어 글이
뒤섞인다.

**저장까지 가서 확인한다.** 되돌리기가 버퍼만 고치고 로그를 그대로 두면 화면은
멀쩡한데 저장이 지운 상태를 보낸다 — 그 어긋남은 저장을 해 봐야 드러나므로,
`dd` → `u` → `p` 뒤에 실제로 자가검증 저장을 통과하는지 보는 시험을 둔다.

### 저장은 자가검증을 통과해야 한다

`:w` 는 이 순서로 간다. 하나라도 어긋나면 **원본을 건드리지 않는다.**

1. 메모리에서 "이렇게 되어야 한다" 를 계산한다 (쌓인 연산을 글자에 그대로 적용)
2. rhwp 에 연산을 일괄 재생해 임시 파일을 만든다 — 우리는 바이트를 만들지 않는다
3. 임시 파일을 **독립 증인**으로 읽는다 (rhwp 아닌 코드)
4. 1 과 3 을 맞춘다 — 본문, 컨테이너 부품 목록, 단락 수
5. 맞을 때만 자리를 바꾸고 원본은 `.hwp.bak` 으로 남긴다
6. 틀리면 멈추고 무엇이 달라졌는지 말한다

**`--force` 는 없다.** 무엇이 틀렸는지 모르는 채로 남의 문서를 덮지 않는다.
쓰기를 한 쪽이 그 쓰기를 검증하면 같은 버그를 두 번 통과하므로, 검증자는 늘
작성자와 다르다.

### 표를 그린다

한국 공문서는 대개 표다 — 이 코퍼스만 해도 표 126개, 누름틀 7개다. 표를 그리지
않으면 서식 문서는 **빈 쪽**으로 보인다(s16.hwp 1쪽이 실제로 그랬다).

```
┌─────────┬──────────────────┬───────────────────────────┬──────────────┐
│기 관    │제출처(온라인)    │세부 경로                  │문의처        │
├─────────┼──────────────────┼───────────────────────────┼──────────────┤
│농식품부 │http://www.iris.go│수요조사 - 정기 수요조사 – │061-338-9756, │
│         │.kr               │부처선택(농식품부)         │061-338-9725  │
└─────────┴──────────────────┴───────────────────────────┴──────────────┘
```

병합을 다루는 규칙은 하나다 — 칸마다 **어느 셀의 땅인지** 적어 둔 지도를 만들면
"두 칸 사이에 선이 있다 ⟺ 주인이 다르다" 로 줄어들고, 교차점 모양(`┼ ├ ┤ ┬ ┴`)도
그 점에서 뻗는 네 방향 선분 유무로 따라 나온다. 특수 경우를 손으로 나열하지 않는다.

열이 너무 많아 터미널에 들어가지 않으면 **넘치게 둔다.** 1칸짜리 열로 억지로
밀어넣어 못 읽게 만드는 쪽이 더 나쁘다 — 가로 스크롤(`<` `>`)에 맡긴다.

### 그림은 색으로 본다 — `v` 로 크게

**1비트 점 그림으로는 로고를 알아볼 수 없다**는 보고를 받았다(2026-10-12). 원인을
재어 보니 분명했다:

| | 원본 | 본문에 그려진 크기 | 점 수 |
|---|---|---|---|
| 로고 | 1315×345 PNG | 34칸×4줄 | **34×8점** (원본의 0.6%) |
| 배너 | 2017×296 JPEG | 44칸×6줄 | 44×12점 |

34×8점을 1비트로 떨구면 로고가 통째로 켜지거나 꺼진다. 두 가지를 바꿨다.

#### 1. 색을 쓴다 — 한 칸에 색 픽셀 둘

반블록 `▀` 에 **글자색과 바탕색을 따로** 주면 한 칸이 위·아래 두 픽셀이 된다. 터미널
이미지 뷰어(chafa·timg)가 쓰는 방식이고, **로고는 모양보다 색으로 가린다.**

눈으로 확인할 수 없으니 **화면의 칸 색을 세는 시험**을 두었다:

```
본문 그림: 반블록 칸 324개 · 서로 다른 (글자색,바탕색) 168가지
```

1비트였다면 **두 가지**(켜짐·꺼짐)다. 이제 기본값이 색이고, `z` 가
색 → 반블록 → 점자 → ASCII → 자리만 → 끔 으로 돈다.

세 가지 예외가 있다:

- **`NO_COLOR`** 면 색을 쓰지 않고 반블록으로 시작한다.
- **넓게 그리는 터미널**에서는 `▀`(Ambiguous)이 두 칸으로 나와 줄이 밀리므로
  **공백 + 바탕색**으로 간다 — 한 칸에 한 픽셀이지만 폭이 보장된다. 세로 해상도를
  절반 잃는 대신 밀리지 않는다(선 문자를 ASCII 로 바꾼 것과 같은 판단).
- **표 칸 안**은 색을 못 쓴다. 격자가 글자 줄(`Vec<String>`)을 합쳐 테두리를 그리므로
  칸마다 색을 실을 자리가 없다. 거기서는 반블록으로 떨어지고, 색으로 보려면 `v`.
- **`hwp page`** 도 색을 쓰지 않는다. 파이프로 가는 글에 ANSI 를 섞으면 받는 쪽이
  폭을 잘못 센다.

#### 2. `v` — 화면을 다 쓰는 창

문서가 놓은 크기를 따르는 것은 **배치 충실도**에는 맞지만 **알아보기**에는 틀렸다.
`v` 가 커서 단락(또는 지금 표 칸)의 그림을 화면 가득 띄운다.

```
┌ 그림 1/6 — 표1 1행1열 ───────────────────────────────────────────────────────────┐
│ ████████████████████████████████████████████████████████████████████████████████ │
│ … 11줄 …                                                                         │
│ BIN0002.png · PNG 1315×345 · 22 KB · 82칸×11줄 · 색 픽셀 1804개                  │
│ n/p 다음·앞 그림 · Esc 닫기                                                      │
└──────────────────────────────────────────────────────────────────────────────────┘
```

**1,804 색 픽셀** — 본문 인라인의 34×8=272 흑백점에서 6.6배다. 원본 크기와 형식도
함께 적는다. 무엇을 보고 있는지 알아야 한다.

`v` 는 vi 에서 블록 지정이다. 아직 블록이 없어 비어 있고, 넣을 때는 `V`(또는 HWP 의
`F3`)로 간다 — 그때 이 자리를 옮기지 않으려고 미리 적어 둔다.

### 그림은 점자로도 본다

```bash
hwp img 문서.hwp                        # 어느 단락에 무슨 그림이 있나
hwp img 문서.hwp --dots 3 --width 76    # 3번 그림을 점자로
hwp img 문서.hwp --dots 3 --glyphs blocks  # 점자가 안 보이는 터미널이면
hwp view 문서.hwp --images braille       # 본문 안에서 제자리에
hwp page 문서.hwp --images placeholder   # 자리와 정체만 네모로 (기본)
```

`--images` 와 `--glyphs` 가 받는 값: `placeholder` · `braille`(=`dots`) ·
`blocks` · `ascii` · `none`.

**터미널 없이 화면을 확인하려면** `--frame` 을 쓴다. 쪽 경계·표·그림·커서가
전부 글로 나오므로, 문제를 알릴 때 이 출력을 붙이면 상대가 무엇이 그려졌는지
본다. 그리는 쪽이 순수 함수라서 가능하다.

```bash
hwp view 문서.hwp --frame 92x26 --images blocks
```

**터미널 글꼴에 점자가 없으면 네모로 보인다.** 그때는 `blocks` 를 쓴다 — 한 칸에
1×2 점이라 해상도는 점자의 1/4 이지만 어느 글꼴에나 있다. 보이지 않는 고해상도보다
보이는 저해상도가 낫다. 확인하는 방법:

```bash
printf '점자: \xe2\xa3\xbf\xe2\xa0\x81  블록: \xe2\x96\x88\xe2\x96\x80\n'
```

점자(U+2800)는 **한 칸에 2×4 점**을 담아 블록 문자의 8배, 반블록의 4배 해상도가
나온다. 1비트로 떨구므로 **Atkinson 디더**를 쓴다 — 1984년 매킨토시가 흑백 화면에
쓴 그 알고리즘이고, Floyd–Steinberg 보다 오차를 덜 퍼뜨려 선과 글자가 뭉개지지
않는다. 레트로 도트의 결이 그대로 나오는 것은 부수적인 이득이다.

**투명한 자리는 흰 종이로 친다.** `to_luma8` 은 알파를 무시하고, 투명 픽셀의 RGB 는
보통 (0,0,0) 이라 투명한 배경이 **새까맣게** 읽힌다. 코퍼스 첫 그림이 그랬다 —
84%가 완전 투명한 로고 띠인데 알파를 무시하면 픽셀의 75%가 어둡고(흰 종이에
합성하면 14.5%), 아래의 자동 반전까지 걸려 사람이 보는 것과 **정반대**가 나왔다.
문서에 놓인 그림은 흰 종이 위에 있다.

그리고 두 가지를 더 한다. **밝기 범위를 펼치고**(흐린 스캔이
통째로 칠해지지 않게), 켜질 점이 과반이면 **스스로 뒤집는다** — 점자는 켜진 점이
잉크이므로 잉크가 다수면 칸이 통째로 `⣿` 가 되어 정보가 0 이 된다. 실측: 코퍼스의
첫 그림은 어두운 배너에 흰 글씨인데 픽셀의 75%가 어두워 전부 칠해졌다.

그릴 수 없는 형식이면 자리만 네모로 알린다. **그림이 있다는 사실을 숨기지 않는다** —
`￼` 를 날것으로 찍어 빈 네모로 보이게 두는 것이 "그림이 안 보인다" 의 원인이었다.

#### 문서가 놓은 크기와 자리로 그린다

`hwp img` 의 `문서 415×32pt · 왼쪽` 이 그 값이다. 본문에 그릴 때는 그 크기를
**본문 폭에 대한 비율**로 바꿔 칸 수를 정하고, 정렬이 가운데·오른쪽이면 그만큼
민다. 10칸이 안 되게 작은 그림은 점을 찍어도 아무것도 안 보여서 `[그림 1 · …]`
한 줄로 줄인다.

그림을 다 단 폭 전체로 그리면 **본문 폭 2% 짜리 아이콘이 전면 배너로 보인다**
(p.hwpx 의 11×33pt 그림이 그랬다). 반대로 배너는 작아 보인다.

크기를 읽는 자리는 포맷마다 다르고, 둘 다 **실측으로** 잡았다.

| | 어디서 | 확인한 방법 |
|---|---|---|
| HWP5 | `CTRL_HEADER` 의 `gso ` 공통속성 `[16..20]` 너비 · `[20..24]` 높이 | 백엔드 조판기의 `export-render-tree` bbox 와 맞춰 봤다 — 코퍼스 HWP5 그림 **20개가 20개 다 1pt 안에서 같다** |
| HWPX | 그림의 `hp:orgSz` × 그 그림 `hp:renderingInfo` 안 `hc:scaMatrix` **전부의 곱** | `hp:sz` 를 가진 맨 바깥 그림 **13개가 13개 다 1% 안에서 같다** |

HWPX 에서 형제 `hp:sz` 를 읽는 쪽이 간단해 보이지만 그건 **맨 바깥 개체에만**
있다. 묶음(`hp:container`) 안의 그림은 자기 `hp:sz` 가 없어서 s14.hwpx 의 그림
15개 중 8개가 빈칸으로 나왔고, 묶음에 둘 이상 들어 있으면 `hp:sz` 는 묶음 전체의
크기라 각 그림의 크기가 아니다. 배율 쪽은 겹친 묶음 수만큼 행렬이 쌓이고 그 곱이
바깥 크기를 정확히 되돌린다. 행렬의 **부호는 뒤집기이지 크기가 아니다** — 절댓값을
쓴다(p.hwpx 는 `e1 = -0.172642` 인데 바깥 `hp:sz` 는 양수 1098 이다).

정렬 비트는 **지어내지 않고 만들어서 확인했다.** 코퍼스의 HWP5 그림 20개가
전부 왼쪽·글자처럼이어서 코퍼스만으로는 시험할 수 없었다. 그래서 s03.hwpx 의
`hp:pos` 를 한 속성만 바꿔 네 벌로 만들고 `rhwp convert` 로 HWP5 로 되돌려
비트를 읽었다. 바꾼 속성 하나당 비트밭 하나만 움직였다:

| 만든 것 | `gso ` 속성 | bit 0 | bits 10–12 |
|---|---|---|---|
| treatAsChar=0 LEFT | `0x042a2210` | 0 | 0 |
| treatAsChar=0 CENTER | `0x042a2610` | 0 | 1 |
| treatAsChar=0 RIGHT | `0x042a2a10` | 0 | 2 |
| treatAsChar=1 LEFT | `0x042a2211` | 1 | 0 |

그래서 **bit 0 = 글자처럼 취급**, **bits 10–12 = 가로 정렬**(0 왼쪽 · 1 가운데 ·
2 오른쪽)이다.

#### 표 칸 안의 그림은 그 칸에 그린다

**코퍼스 그림 43개 중 23개가 표 칸 안에 있다.** 처음에는 전부 표 **아래**에
쌓아 그렸는데, 그러면 자리가 완전히 틀린다 — s00.hwp 2쪽의 로고 두 개는
1행 2열 표의 두 칸에 들어 있어서 문서에서는 **같은 줄 양끝**이다.

```
  18
      ┌───────────────┬────────────────┐
      │⠀⢀⠀⠀⠀⠀⡀⠀⠀⣀⠀⠀⠀⠀⠀│⢠⡶⢶⡄⢀⣀⠀⡀⣀⣀⣀⣀⣀⡀⣀⡀│
      │⠀⣯⡇⢳⢃⣀⡥⣄⣰⢉⣹⣆⡯⢸⠀│⣸⣁⠎⣿⠰⣻⢞⡷⣾⢾⡹⣼⢿⡛⣤⠇│
      └───────────────┴────────────────┘
```

칸 좌표는 HWP5 는 `LIST_HEADER` payload `[8..12]` 의 `(col, row)`, HWPX 는
`hp:cellAddr` 에서 읽고, 표 번호는 레코드 순서로 센다. **표 번호·행·열이
백엔드 `export-tables` 와 전수 일치한다(23개 중 23개)** — 두 판독이 따로
읽어 같은 칸을 가리킨다. 어긋나면 그림이 엉뚱한 칸에 그려지는데 표는 멀쩡히
그려지므로 보기에 아무 문제가 없다. 그래서 대조가 필요하다.

HWPX 의 `hp:cellAddr` 는 칸 **내용 뒤에** 온다(`hp:tc` → `hp:subList` →
단락들 → `hp:cellAddr`). 그림을 만들 때는 좌표를 아직 모르므로 좌표가 오면
되돌려 찍는다. 앞에서 찍어 두려다 s14.hwpx 의 칸 안 그림 9개를 전부 놓쳤다.

그림이 든 칸은 **원하는 폭을 표에 먼저 말한다**(`Cell::min_width`). 그림은
칸 폭에 맞춰 그리고 칸 폭은 내용이 필요한 만큼을 보고 정하므로, 그림의 폭을
글자처럼 재면 서로를 기다린다. 이게 없으면 글자 없는 그림 칸이 4칸으로
쪼그라들어 `[그` 까지만 보인다.

칸이 좁으면 표시도 **폭에 맞춰** 줄인다 — `[그림 1]` → `[1]` → `▣`. 한 가지
모양으로 찍고 자르면 p.hwpx 의 4칸 화살표 칸이 `[그 ` 가 되는데, 잘린 글자는
아무것도 알려주지 않는다. 지금은 이렇게 나온다:

```
      │현재(AS-IS)│[1] │1단계 완료(‘32)│[2] │미래(TO-BE)│
```

**아직 안 하는 것:** 표 밖에서 한 단락에 그림이 둘 이상일 때의 가로 오프셋.
그때는 위아래로 쌓는다.

### 글머리와 들여쓰기

**글머리표는 실제 글자다.** 코퍼스 664단락에서 조판기가 그리는 글자와 우리
글자를 전수 대조했고 한 군데도 다르지 않다 — `□` `○` `-` `①` 이 문단 속성이
아니라 본문에 들어 있다. 그래서 글머리는 이미 제대로 보이고, 단계를 옮기는
일도 **글자 편집**이라 검증된 저장 경로를 그대로 탄다.

### 문단서식 — 뭘 담고 뭘 버리는가

HWP 문단서식에는 왼쪽·오른쪽 여백, 들여쓰기, 문단 위·아래 간격, 줄 간격,
탭 설정이 들어 있다. **쓰임을 재서 담을 것을 골랐다.** 코퍼스 본문 795단락:

| 속성 | 0 아닌 단락 | 흔한 값 | 판정 |
|---|---|---|---|
| **들여쓰기(`intent`)** | **63%** | 전부 음수 — `-5166` `-3639` `-3331` | **담는다** |
| 문단 위 간격 | 42% | 500·1000·300 | 버린다 |
| 문단 아래 간격 | 28% | 500·100·300 | 버린다 |
| 왼쪽 여백 | 4% | 831·600·1330 | 들여쓰기 계산에만 |
| 오른쪽 여백 | 0.6% | 775 하나뿐 | 버린다 |
| **정렬** | 가운데 6% + 오른쪽 5% | — | **담는다** |

오른쪽 여백은 코퍼스 전체에서 쓰는 단락이 5개다. 간격은 값은 깔끔한데
(5pt·10pt·3pt) 빈 줄로 그리면 조판기가 준 쪽·줄 수와 어긋난다. 반면
**들여쓰기는 쓰는 쪽이 다수이고, 값이 잡값인데 뜻은 필수다.**

#### 내어쓰기가 다수다 — 그리고 조판기가 안 알려준다

63%의 음수 들여쓰기는 **내어쓰기**다. 글머리를 왼쪽에 두고 이어지는 줄을 글
아래로 맞추는 바로 그 장치다. 규칙은

```
첫 줄   = 왼쪽여백 + max(들여쓰기, 0)
이후 줄 = 왼쪽여백 + max(-들여쓰기, 0)
```

조판기 렌더트리의 줄별 x 와 맞춰 **21개 맞음 / 0개 틀림**(나머지는 한 줄
단락이라 시험 불가).

처음에는 조판기의 `lineSegs.columnStart` 만 읽었는데 **그 값은 첫 줄만 말하고
내어쓰기 문단에서 `(0, 0)` 을 돌려준다** — s03.hwpx 단락3 은 `intent=-3114`
로 둘째 줄이 31.1pt 들어가는데 columnStart 는 0 이다. 그래서 문단서식을
증인이 직접 읽는다.

그 판독이 맞는지는 `columnStart` 가 지킨다: **증인의 첫줄 들여쓰기가 조판기의
columnStart 와 코퍼스 전수 670/670 일치**한다. 두 판독이 따로 읽어 같은 값에
닿는다.

`textStart` 와 혼동하지 말 것 — 그쪽은 줄이 단락의 몇 번째 **글자**에서
시작하는지라 s00 에서 179줄 중 2줄만 0 이 아니고 값이 50·51 이다. 들여쓰기로
읽으면 500pt 가 되어 쪽을 벗어난다.

#### HWP5 의 여백 단위는 HWPUNIT 의 **절반**이다

실측으로 확정했다. s00.hwp 의 `PARA_SHAPE[245]` 가 들여쓰기 `-3506` 을 들고
있고, 그 서식을 쓰는 단락 105·107 의 둘째 줄이 렌더트리에서 본문+**17.6pt**
에 그려진다 (`3506/200 = 17.5`, `3506/100 = 35.1` 이 아니다). 변환된 HWPX 의
`hh:margin` 값도 정확히 절반(`-1753`)이다 — 두 출력이 같은 말을 한다.

**이것이 앞서 `apply-para-format` 이 "절반만 반영"되어 보인 이유다.** 백엔드가
받은 수를 HWPUNIT 이 아니라 저장 단위(½ HWPUNIT)로 그대로 적는다. 크기를
잘못 다루는 것이 아니라 단위가 어긋난 것이다. (모르는 키를 조용히 무시하는
문제는 그대로 남아 있다.)

HWPX 쪽은 `hh:margin` 이 이미 HWPUNIT 이니 나누지 않는다. 다만 `hp:switch`
안에 HWPUNIT 판과 글자 단위 판이 **두 벌** 적혀 있어서, 먼저 나오는 쪽을
그냥 읽으면 단위가 섞인다 — `hp:required-namespace` 가 `HwpUnitChar` 인
`hp:case` 를 골라야 한다.

#### 표 칸은 가운데가 다수다 — 본문과 반대다

| | 가운데 | 양쪽맞춤 | 오른쪽 | 왼쪽 |
|---|---|---|---|---|
| 표·글상자 안 (2357단락) | **64%** | 25% | 5% | 4% |
| 본문 (795단락) | 6% | **76%** | 5% | 11% |

전부 왼쪽으로 그리면 공문서 표가 서식처럼 보이지 않는다. 지금은 이렇게 나온다:

```
      ┌──────────────┬────────────────────────────────────────┐
      │    기 관     │          조사 분야(주요 내용)          │
      ├──────────────┼────────────────────────────────────────┤
      │농림축산식품부│ㅇ (산업화 분야) AI·디지털 전환,        │
```

머리 칸은 가운데, 내용 칸은 양쪽맞춤이라 왼쪽 — 문서가 그렇게 돼 있다.

칸 정렬은 **증인이 읽고 백엔드의 표에 좌표로 맞춰 채운다.** 백엔드
`export-tables` 는 글자만 주고 정렬을 주지 않기 때문이다. 표 번호·행·열이
두 판독에서 같다는 것은 그림 작업에서 전수(23/23) 확인했다.

열 폭은 내용에 맞춰 정해지므로(표는 단 폭을 다 쓰지 않는다) 가운데로 밀 자리는
**다른 행이 그 열을 넓혔을 때** 생긴다. 공문서 표의 머리 칸이 가운데로 보이는
것이 바로 그 모양이다.

#### 안 하는 것

- **문단 간격·줄 간격.** 빈 줄로 환산하면 조판기가 준 쪽·줄 수와 어긋난다.
- **세로 정렬**(`vertAlign`). 행 높이가 내용으로 정해지므로 기준이 없다.
- **오른쪽 여백.** 코퍼스 전체에서 5단락.
- **양쪽맞춤.** 터미널이 글자 사이를 늘릴 수 없다. `Justify` 는 들고 있지만
  (그래서 `hwp json` 이 쓸 수 있다) 왼쪽으로 그린다.

문단서식을 직접 보려면 `hwp witness <파일> --style --text`.

#### Tab / ⇧Tab — 문서가 쓰는 사다리를 따라간다

`hwp edit` 에서 `Tab` 은 글머리 단계를 한 칸 들이고 `⇧Tab` 은 한 칸 내온다.
들여쓰기 칸 수와 기호를 **그 문서에서 읽어** 쓴다. `hwp toc` 이 사다리를
보여준다:

```
$ hwp toc 과업지시서.hwp
단계 사다리 (에디터에서 Tab / ⇧Tab 이 이 표를 따라간다)
  1단계  들여쓰기 0칸  번호 글머리 (Number, 예 `8.`) — 번호는 직접
  2단계  들여쓰기 1칸  기호 `○` 로 바꿈
  3단계  들여쓰기 3칸  기호 `-` 로 바꿈
```

사다리를 하나 박아 두면 안 된다. 공문서의 단계는 문서마다 다르다 — s00 은
`□(0칸) □(2칸) -(3칸)`, s13 은 `번호(0칸) ○(1칸) -(3칸)`, s02 는 5단계다.

두 가지를 **하지 않는다.**

- **세어지는 글머리**(`1.` `가.` `①`)로 옮길 때는 들여쓰기만 옮기고 기호는
  원래 것을 둔 뒤 그렇게 말한다. 번호는 그 자리에서 몇 번째인지에 달려 있어
  다른 단락의 표본을 붙이면 **틀린 번호**가 들어간다. 실제로 대표값으로
  `8.` `6.` `나.` 가 뽑혔다.
- **글머리가 없는 단락**에는 글머리를 붙이지 않고 들여쓰기만 옮긴다. 달라고
  하지 않은 기호를 넣는 것은 글자를 만들어 내는 일이다.

`<` `>` 는 넓은 표를 볼 때 가로 스크롤로 쓰고 있어 건드리지 않았다.

#### 문단 속성으로서의 들여쓰기는 아직 못 쓴다

백엔드의 `edit apply-para-format` 으로 `marginLeft`·`indent` 를 쓰려 했는데
실측에서 세 가지가 걸렸다 (rhwp 0.8.7):

| 넣은 값 | 결과 (`columnStart`/`segmentWidth`) |
|---|---|
| 원본 (s00 단락58) | 600 / 47588 |
| `{"marginLeft":2000}` | 0 / 47188 — 폭이 **1000** 만 줄었다 |
| `{"marginLeft":4000}` | 0 / 46188 — 역시 **절반** |
| `{"indent":2000}` | 0 / 47588 — 들여쓰기가 생기지 않는다 |
| `{"indentation":2000}` 등 오타 | 600 / 47588 — **아무 말 없이 무시** |

요청값의 절반이 들어가고, 모르는 키는 조용히 지나간다. 이 상태에서 단축키를
붙이면 **말한 것과 다른 값을 쓰는 단축키**가 된다. 그래서 글자 쪽(Tab)만
내놓고 문단 속성 쪽은 보류했다.

쓰려면 먼저 백엔드에 올려 고쳐야 한다 — 특히 **모르는 키를 조용히 무시하는
것**이 위험하다. 오타 하나가 "적용됐다"는 응답과 함께 아무 일도 하지 않는다.

### 서식 채우기

한국 서식은 대개 누름틀이 아니라 **표**로 되어 있다(이 코퍼스에서 누름틀은 3개
파일에 7개, 표는 14개 파일에 126개). 그래서 채우는 길은 셀 쓰기다.

```bash
hwp cells 신청서.hwp --table 0            # 좌표를 먼저 본다
hwp set-cell 신청서.hwp \
  "0:1:1=차세대 디지털육종 기반 기술개발" \
  "0:3:1=○○대학교" -o 신청서_작성.hwp
```

셀 쓰기도 같은 자가검증을 지난다 — 고른 셀에 값이 들어갔고 **다른 셀은 하나도
움직이지 않았음**을 독립 증인이 확인한 뒤에 저장한다.

### 기호는 문자표에서 고른다 — `Ctrl-K`

터미널에 한글 IME 가 있어도 `○` `□` `※` `①` 을 넣을 길이 없다. 두벌식 오토마톤은
한글만 만든다. 그런데 **공문서는 그 기호들로 계층을 만든다** — 없으면 공문서를 쓸 수
없다. HWP 는 이 일을 문자표(`Ctrl-F10`)로 한다.

```
┌ 기호 넣기 ─────────────────────────────────────────────┐
│ 글머리   번호   화살표   괄호·따옴표   수·단위   그 밖 │
│                                                        │
│« ○  » □   ◦   ※   ·   •   ◾  ▶                          │
│ ☞   ◈   ●   ■   ◆   ◇   △   ▲                          │
│ ▽   ▼   ▪   ◯                                          │
│                                                        │
│ ○  흰 동그라미 — 코퍼스 128회, 2단계 글머리            │
└────────────────────────────────────────────────────────┘
 ←→/ad 고르기 · ↑↓/ws 줄 · Tab 묶음 · ↵ 넣기 · Esc 닫기
```

**키는 `Ctrl-K`** — vi 가 **끼워넣기 모드**에서 digraph(특수문자)를 받는 자리다. 보통
모드의 `Ctrl-K`(워드스타 블록 묶음)와 겹치지 않는다: 끼워넣기 모드는 그 분기에서
끝나고 도스 키 표를 보지 않는다. **두 계보가 같은 결론에 와 있다.** `Ctrl-F10`(HWP의
키)도 터미널이 보내 주면 받고, 메뉴와 `:sym` 으로도 열린다. 표 칸을 고치는 중에도
같은 키다 — 칸 고치기가 끼워넣기 모드를 그대로 쓰기 때문이다.

#### 무엇을 담을지 짐작하지 않았다

코퍼스 14개 문서의 본문과 표 칸에서 한글·한자·ASCII 를 뺀 글자를 전수로 세었다
(2026-10-11, 서로 다른 기호 **57개**):

```
·  165   ○  128   □  123   ’   90   ◦   53   ※   50
×   26   •   17   –   15   ◾   14   ∼   14   ▶   13
→   13   ①    8   ②    8   「」  7   ③    6   ☞    5
```

그래서 **글머리가 첫 묶음**이고 그 안에서도 `○ □ ◦ ※` 가 앞이다. 쓰지도 않는 기호를
가나다순으로 늘어놓으면 매번 찾아 헤매게 된다. 고른 기호의 **뜻**을 상자 안에 적는
것도 그래서다 — 모양만 보면 `○` `◦` `◯` 와 `□` `■` `▪` 를 가릴 수 없다.

담지 않은 것: **사용자 영역**(`U+F007E` 등, 코퍼스에 6번 — 한컴 글꼴의 자체 글립이라
다른 곳에 붙이면 네모로 보인다), 공백·마침표의 변종(`U+2007` 74번, `U+2024`), 글자에
붙어 쓰이는 수정 문자(`ʻ ʼ ˮ`).

반각 변종(`･` `｢` `｣`)은 **담았다.** 전각과 거의 똑같이 보여 눈으로는 가릴 수 없지만
코퍼스가 쓰고 있고(`･` 13회), 그 문서를 고치는 사람은 같은 글자로 이어 써야 한다.
처음엔 뺐다가 **코퍼스 대조 시험이 잡았다** — 두 번 이상 나온 기호가 표에 다 있는지
보는 시험이다. 새 문서를 코퍼스에 넣었는데 그 문서의 글머리를 고를 수 없으면 그때
걸린다.

기호 자체는 넓은 터미널에서도 **ASCII 로 바꾸지 않는다.** 테두리와 안내줄은 우리
장식이라 바꾸지만, `○` 를 `o` 로 보여 주면 **고른 것과 넣는 것이 달라진다.** 그래서
기호 하나에 네 칸을 주고 표시 폭으로 채운다 — 두 칸인 기호가 와도 상자를 넘지 않는다.

기계 쪽은 글자를 그냥 넣으면 된다(`insert-text`). 대신 **어떤 기호가 있는지**를
읽을 수 있다 — `read: ["symbols"]`. 단계마다 어느 글머리를 쓰는지 알아야 하므로.

### 한자는 `F9` — 커서 앞 음절을 바꾼다

HWP 와 같은 키다. 커서 앞의 한글 음절을 보고 같은 음으로 읽는 한자를 늘어놓는다.

```
┌ 과 → 한자 ──────────────────────────────────────────┐
│                                                     │
│« 果 » 過  科  課  寡  誇  瓜  戈                      │
│ 菓  顆  袴  蝸  跨  鍋  裹  夸                      │
│ 窠  夥  媧  胯  撾  侉  踝  銙                      │
│                                                     │
│ 果  실과 과, 과실 과                                │
│ ←→/ad 고르기 · ↑↓/ws 줄 · ↵ 넣기 · Esc 닫기  [1/105]│
└─────────────────────────────────────────────────────┘
```

**더하지 않고 바꾼다.** 더하면 `과果` 가 되고 그건 아무도 원한 적이 없다. 기호표와
같은 상자를 쓰면서 이 하나가 다르다(`Picker::replace`). 낱말은 음절을 이어 바꾼다 —
`과`→`課`, `업`→`業` 로 `課業`.

커서 앞이 한글 음절이 아니면 **열지 않고 왜인지 말한다.** 빈 상자를 띄우면 "표가
비었나" 로 읽힌다. 조합 중인 자모(`ㅘ`)도 음절이 아니다 — 그래서 `F9` 는 먼저 조합을
확정한다(확정하지 않으면 "커서 앞에 글자가 없다" 고 답했다. 처음에 그랬다).

후보가 백 개를 넘으므로(`과` 105개, `부` 249개) 상자가 **넘긴다**. 화면을 다 덮으면
무엇에 대고 하는 일인지 보이지 않는다.

#### 표는 짓지 않았다 — 가져왔다

한글 음과 한자의 대응은 **사전 데이터**다. 지어내면 틀린 글자를 가르친다. 출처는
libhangul 의 `data/hanja/hanja.txt` 이고 **BSD-3-Clause** 다 — libhangul 본체는
LGPL 이지만 이 데이터 파일은 따로 BSD-3 이라 MIT 인 이 프로젝트에 담을 수 있다.
저작권 표시와 라이선스 전문을 `crates/hwp-core/data/` 에 함께 둔다.

담은 것은 **키가 한글 음절 한 글자**인 항목 — 555음절 28,472자, 311 KB. 원본의 낱말
항목 22만여 개(`과업:課業`)는 **6.3 MB 라 넣지 않았다.** 음절 단위가 한자 키의 본래
동작이고, 낱말은 음절을 이어 바꾸면 된다. 순서는 원본 그대로다 — 중요한 글자가 앞에
온다(`한` → 韓 漢 寒 限 閑 恨). 가나다순으로 다시 늘어놓으면 매번 찾아 헤매게 된다.

새김이 없는 글자는 `(새김이 없는 드문 글자)` 로 적는다. 목록 뒤쪽에 몰려 있고,
사전에 새김이 없다는 것 자체가 "이건 아마 네가 찾는 글자가 아니다" 라는 정보다.

`hwp doctor` 가 두 표의 크기를 말한다 — 바이너리에 박아 넣으므로 "왜 `F9` 가 안
되지" 를 거기서 가를 수 있어야 한다.

```
  넣을 글자
    기호           6묶음 101개 — `Ctrl-K` (코퍼스가 쓰는 순서)
    한자           555음절 — `F9` (libhangul hanja.txt, BSD-3)
```

기계 쪽은 `hanja: "과업"` — 음절마다 후보를 돌려준다. **고르는 것은 부른 쪽의
일이다**: 음이 같은 한자가 백 개를 넘고 뜻이 다 다르므로, 첫 후보를 말없이 집어
넣으면 엉뚱한 글자가 문서에 들어간다.

### 두벌식은 직접 조합한다

`:set ime=2` 를 켜면 터미널 IME 없이 한글을 친다. 터미널 IME 는 조합 중 글자를
우리 화면 **위에** 그려서 버퍼가 볼 수 없고, 원격 접속 세션에는 IME 가 아예 없다.
초성·중성·종성 상태기계로 조합하고 커서 자리에 조합 중인 음절을 밑줄로 보여준다.
겹모음·겹받침, 받침이 다음 초성으로 넘어가는 것(`간`+`ㅏ`→`가나`), 자모 단위
되돌리기까지 한다.

### 커서는 rhwp 좌표다

커서는 `(구역, 단락, 오프셋)` — `edit --section N --para M --offset K` 와 같은
좌표계다. 화면 자리에서 좌표를 계산하지 않고 좌표에서 화면 자리를 계산한다.
그리고 **rhwp 의 오프셋은 인라인 컨트롤을 세지 않는다**(실측), 그래서 버퍼는
보이는 글자만 담는다. 그림이 든 단락은 여백에 `◻`, 고친 단락은 `*` 로 표시한다.

### `hwp json` — LLM 이 읽기 쉬운 출구

프로파일로 토큰을 고른다 (15쪽·표 24개 공고문 기준):

| 프로파일 | 담는 것 | 크기 |
|---|---|---|
| `text` | 본문만 | 10.1 KB |
| `outline` | 개요 트리 | 7.9 KB |
| `doc` (기본) | 개요 + 본문순서 + 표 격자 | 32.5 KB |
| `full` | + 구역 메타 | 32.5 KB |

(비교: `rhwp dump` 167 KB, `export-structure`+`export-tables` 28 KB)

모든 항목이 rhwp 편집 좌표 `(section, para)` 를 들고 있어서 **읽고 바로 고치는 고리가
닫힌다**: `hwp json` → LLM → `hwp edit`(같은 좌표) → `hwp view` 로 확인. 페이저 커서와
같은 좌표계다.

**빈 단락도 넣는다 — 좌표를 숨기면 고칠 수가 없다.** 전에는 글자가 빈 단락을
건너뛰었다(토큰을 아끼려고). 그런데 이 JSON 의 약속이 바로 위 문장이고, 빠뜨리면 그
고리가 끊어진다. 실측(2026-10-10): 이 표의 기준 문서는 본문 102단락 중 **53개가
빈 단락**이어서 절반 넘게 사라져 있었고, s16.hwp 는 **13단락이 전부** 사라져 "본문
단락이 하나도 없는 5쪽 문서" 로 보였다(13개가 다 표·그림만 든 빈 단락이다). 그 상태로는
어디에 줄을 넣을지 고를 좌표가 없다 — 사람은 화면 왼쪽 여백에서 그 번호를 본다.
대가는 빈 단락 하나에 46바이트이고, `text` 가 7.8 → 10.1 KB 가 되었다.

문서 본문은 `untrusted: true` 와 `untrustedFields` 로 표시된다. **공문서를 LLM 에 넣을
때 문서 안의 문장이 모델에게 지시로 읽히면 그게 주입이다.** rhwp 의 관례를 승계하고
재발명하지 않는다.

**개요 트리는 공문서 글머리에서 만든다** — rhwp 의 `export-structure` 는 `--mode
auto|outline|clause` 세 모드 모두 `roots=0` 이다(샘플 6건 전수). 레벨은 코퍼스 전수
조사로 정했다: 같은 기호가 들여쓰기 0·1·2 에 다 나오고(`○` 85/15/3 회) `※`·`*` 는
들여쓰기와 무관한 **주석**이라, 기호 하나로도 들여쓰기 하나로도 정해지지 않는다.
그래서 `(들여쓰기, 기호분류)` 를 키로 **문서가 실제로 쓴 키만** 모아 레벨을 매긴다 —
`○`·`-` 만 쓰는 문서는 1·2 레벨이 된다. 들여쓰기는 한 칸 오차까지 뭉치고(손으로 띄운
공백이 흔들린다), 레벨 표는 **구역마다 따로** 만든다(붙임 양식의 `1.` 이 본문 계층
아래로 끌려 들어간다).

**쪽 경계와 줄 수는 rhwp 조판값이고, 한 줄 안에서 접히는 위치만 이 프로그램이
계산한다.** 단 폭은 글꼴을 읽지 않고 조판 결과에서 역산한다 — 단락이 n 줄로
조판됐고 표시 폭이 w 칸이면 한 줄 용량은 `ceil(w/n)` 이상이므로, 그 하한들의
최댓값이 본문 단의 폭에 수렴한다. 상태줄이 몇 단락에서 재었는지 말하고, 잴
근거가 없으면 기본값을 썼다고 말한다.

## 기계 쪽 입구 — `hwp api`

사람 쪽이 먼저 자랐다. vi 키·도스 키·메뉴·아래 도움줄이 붙는 동안 기계 쪽은
`json`·`set-para`·`set-cell`·`para` 로 흩어져 있었고, 그 차이는 기능 몇 개가 아니라
**할 수 있는 일의 범위**였다.

| | 전 | 지금 |
|---|---|---|
| 종류가 섞인 편집 | 명령마다 저장 — 중간에 실패하면 반만 고쳐진 문서가 남는다 | **한 요청 = 한 저장** |
| 찾기 (`/`) | 화면에만 있었다 | `find` — 좌표로 돌려준다 |
| 글머리 단계 (`Tab`) | 화면에만 있었다 | `ops: [{"op":"relevel", …}]` |
| 쓰기 전 확인 | 없다 | `dryRun` |
| 정렬·들여쓰기·글자꾸밈 | `witness --style/--deco` 의 사람용 출력 | `read: ["styles","deco"]` |
| 무엇을 할 수 있나 | `?` 도움 (사람만) | `--capabilities` |
| 오류 | 산문, stderr | JSON, 원인 사슬까지 |

```bash
hwp api --capabilities                       # 할 수 있는 일 전부
echo '{"file":"a.hwp","read":["outline"],"find":"예산"}' | hwp api
hwp api -r '{"file":"a.hwp","dryRun":true,"ops":[…]}'   # 쓰기 전에 확인
```

요청 하나, 응답 하나. 읽기와 쓰기를 같은 요청에 섞을 수 있고, **쓰기는 종류가 섞여도
한 번만 저장한다** — 기존 저장 경로의 자가검증(메모리에서 기대값 계산 → rhwp 로 재생
→ 독립 증인으로 재확인 → 바꿔 끼우고 `.bak`)을 그대로 탄다. `--force` 는 여기에도 없다.

### 같음은 한 번 맞추면 끝나는 게 아니다

사람 쪽에 키를 하나 더하면 기계 쪽에도 길이 있어야 한다. 그걸 사람이 기억하는 대신
**컴파일러가 지킨다** — `api::capability_of` 가 편집기의 `Action` 을 **빠짐없이** 받는
`match` 이고, 동작을 하나 더하면 빌드가 깨진다. 실제로 그런지 확인했다:

```
error[E0004]: non-exhaustive patterns: `&Action::SomethingNew` not covered
   --> crates/hwp-cli/src/api.rs:201:11
```

그래서 기계 쪽을 **일부러** 비워 둘 때는 이유를 적어야 하고(`Machine::Absent`),
시험이 그 이유가 비지 않았는지 본다. 지금 비어 있는 셋:

| 일 | 왜 기계 쪽에 없나 |
|---|---|
| 되돌리기 (`u`·`Ctrl-R`) | 요청 하나가 원자적이다 — 틀리면 아무것도 저장되지 않고, 저장은 `.bak` 을 남긴다. 되돌릴 상태를 쥔 세션이 없다 |
| 담기·붙이기 (`y`·`p`) | 담아 둘 자리가 없다. 읽은 글자를 `set-para` 로 그대로 준다 |
| 모드·메뉴·끝내기 | 요청 하나로 끝나므로 쥐고 있을 상태가 없다 |

그리고 **키 목록은 손으로 적지 않는다.** `--capabilities` 의 `keys` 는 편집기가 실제로
쓰는 키 표(`action_for_mode`)를 쓸어서 만든다 — 적어 두면 키를 옮길 때 같이 고치는
것을 잊고, 그 목록은 **틀린 것을 가르친다.** 맨 키와 같은 동작을 하는 조합키는 뺀다
(편집기가 `KeyCode` 로 가르므로 `Ctrl-T` 가 `t` 로 잡힌다 — 같은 동작이면 별도의 키가
아니다).

### 화면도 같은 요청으로 본다

```json
{"file": "s16.hwp", "frame": "78x14", "keys": "Tll"}
```

```
s16.hwp  [hwp5]  표0 1행1열  ·  Tab 다음칸 · Esc 나가기
──────────────────────────* 2 / 5 쪽 *──────────────────────
      ┌─────────────────────────────────────────────────────
      │«              신청 자격의 적정성 확인서            »
      ├─────────────┬───────────────────────────────────────
      │   사업명    │바이오·의료기술개발 > 인공지능바이오
```

커서를 움직이는 키는 기계 쪽에 따로 두지 않았다 — `frame` + `keys` 로 **사람이 보는
그 화면을** 보는 것이 그 일의 전부다.

### 밀린 것과 바뀐 것을 가른다

`changed` 는 `edited` / `added` / `removed` 로 말한다. 단락 하나를 넣으면 뒤쪽 좌표가
전부 한 칸씩 밀리는데, 그것을 "바뀌었다" 로 세면 보고가 수십 줄이 되고 정작 넣은 줄이
묻힌다 — 처음 구현이 그랬다. 그래서 넣고 뺀 자리를 먼저 반영해 같은 글자를 같은 글자에
맞추고, 그래도 다른 것만 보고한다. 번호가 밀렸으면 `wasAt` 으로 어디서 왔는지 말한다.

`ops` 는 **순서대로** 적용되고, 각 연산은 **앞선 연산이 바꿔 놓은 상태**를 본다 —
좌표 셈은 저장 경로가 쓰는 `edit::expected` 를 그대로 쓴다. 두 군데 두면 반드시
어긋난다.

### 상태줄에 뜨던 말도 받는다

사람이 `Tab` 을 누르면 상태줄이 `2단계로 옮겼다`, 또는 **번호를 손으로 고쳐야 한다**고
말한다(목표 단계가 `1.`·`가.` 처럼 세어지는 글머리면 다른 단락의 표본을 붙일 수 없다).
그 줄을 사람만 읽고 기계는 못 읽는다면 같은 기능이 아니다 — `applied[].note` 로 온다.

### `output` 의 확장자는 원본과 같아야 한다

백엔드는 **확장자로 형식을 정한다.** `.hwpx` 를 `.hwp` 로 내보내면 조용히 변환이
일어난다 — 실측으로 ZIP 부품 12개가 사라지고 CFB 스트림 11개가 생겼다. 자가검증이
"컨테이너 부품이 바뀌었다" 로 막아 주었지만(그래서 저 사실을 알았다), 애초에 물어볼
일이라 거부한다. 변환은 `rhwp convert` 로 따로 한다.

## AI 가 문서를 만들고 고치고 저장하는 입구 (2026-10-29)

### 여러 문단인 칸 — `lines` (사용자 보고 2026-10-29)

> "`set-cell` 이 한 줄만 받아서 문단이 여러 개인 칸은 기계가 채울 방법이
> 없습니다. 한국 서식에서 서술형 칸은 거의 다 여러 문단이라 서식 채우기의 큰
> 구멍입니다. **제가 XML 을 직접 고쳐 우회했는데, 그 경로는 자가검증을 타지
> 않습니다.**"

마지막 문장이 이 변경의 이유다 — **도구의 구멍이 사용자를 검증 없는 경로로
밀어냈다.** 실측으로 코퍼스의 글자 있는 칸 1,517개 중 **128개(8%)가 여러
문단**이고 전부 서술형 칸이다(`제출 서류 ⏎ 1) 제출공문: … ⏎ 2) 사업 참여 …`).

```json
{"op":"set-cell","table":0,"row":0,"col":0,
 "lines":["제출 서류","  1) 제출공문 1부","  2) 사업 참여 신청서 1부"]}
```

`text` 는 한 문단, `lines` 는 문단 목록이다. 둘을 함께 주면 거부한다 — 어느
쪽이 이기는지 받는 쪽이 짐작하게 두지 않는다.

**미리보기가 거짓말하던 것도 같이 고쳤다.** 전에 `text` 에 `\n` 을 넣으면
`dryRun` 이 `ok` 로 `after: "첫 문단\n둘째 문단"` 을 약속하는데, 실제 저장은
백엔드에서 거부됐다(`--text 에 줄바꿈·탭은 넣을 수 없습니다`). 지금은 `text` 의
줄바꿈을 **미리** 거부하고 `lines` 를 쓰라고 말한다.

#### 한 연산이 백엔드 명령 여러 개로 펴진다

백엔드의 `set-cell --text` 는 한 줄 값만 받는다. 그래서 문단 목록은 이렇게 간다 —
`set-cell`(첫 문단으로 칸을 통째로 교체) → 문단마다
`split-paragraph-in-cell`(앞 문단 끝에서 쪼갠다) + `insert-text-in-cell --cell-para N`.
`Op::commands` 가 명령 **목록**을 돌려주고 재생 루프가 사슬로 잇는다.

실측으로 확인한 두 가지: `set-cell` 은 여러 문단 칸을 **한 문단으로 접는다**(전체
교체라 그래야 맞다), `split-paragraph-in-cell --offset` 은 **글자 수**로 센다
(`"첫 문단"` 에 offset 3 → `"첫 문"` / `"단"`).

#### 자가검증은 손댈 데가 없었다

증인이 칸 안 문단을 `\n` 으로 이어 읽으므로, 기대값도 그렇게 이으면 대조가
그대로 성립한다. **여러 문단을 쓰는 길이 생겼는데 검증 코드는 한 줄도 안 바뀌었다** —
비교 단위를 처음에 맞게 잡아 둔 값이 여기서 돌아왔다.

사람 쪽도 같이 고쳤다. 화면에서 여러 문단 칸을 고칠 때 `split_cell_lines` 로
문단 경계를 되살리지 않으면 저장하면서 문단이 하나로 접힌다 — 문서를 조용히
고치는 일이다.

### 칸 안의 한 문단만 — `insert-text-in-cell` / `delete-text-in-cell` (사용자 보고 2026-10-29)

> "`set-cell` 은 통째 덮어쓰기뿐입니다. 본문 단락에는 `insert-text`·`delete-text`
> 가 있는데, 셀 문단은 `read:["text"]` 의 body 에 나오지 않아 좌표가 없습니다.
> **한 글자만 고치려 해도 칸 전체를 다시 써야 합니다.**"

통째로 다시 쓰려면 고치지 않을 문단까지 베껴야 하고, **베끼는 자리가 오타가 들어가는
자리**다. 고치는 문단 하나가 아니라 베낀 문단 전부가 위험해진다.

```json
{"op":"insert-text-in-cell","table":0,"row":1,"col":1,
 "cellPara":1,"offset":7,"text":"(고침)"}
{"op":"delete-text-in-cell","table":0,"row":1,"col":1,
 "cellPara":1,"offset":7,"count":4}
```

**좌표는 어디서 오는가.** 칸 안 문단이 `read:["text"]` 에 없는 것은 맞다 — 본문
단락과 칸 문단은 좌표계가 다르고(`구역:단락` 대 `표:행:열:칸문단`), 한 배열에
섞으면 받는 쪽이 어느 쪽인지 구분할 수 없다. 대신 두 곳에서 온다.

- `read:["tables"]` — 칸 글자는 문단을 `\n` 으로 이어 둔 것이다. 그래서
  `grid[row][col].split("\n")` 의 몇 번째인지가 `cellPara`, 그 문단 안에서
  글자를 센 수가 `offset` 이다(둘 다 0부터).
- `find` — **찾은 자리를 그대로 고칠 수 있게** 칸 일치도 `cellPara`·`offset` 을
  들고 온다. 전에는 `table`/`row`/`col` 과 칸 글자 전체만 줬는데, 그걸 받은
  기계가 할 수 있는 일은 통째 덮어쓰기(= 베끼기)뿐이었다. 단락 쪽처럼 **한 칸의
  모든 일치**를 준다.

```bash
# 찾기 → 그 좌표로 바로 고치기
echo '{"file":"a.hwpx","find":"늦다"}' | hwp api
# → {"kind":"cell","table":0,"row":0,"col":0,"cellPara":1,"offset":9,"text":"현장 문제 해결이 늦다"}
```

`find` 의 칸 `text` 는 **그 문단**의 글자다(칸 전체가 아니다). 칸 전체를 되붙여
두면 `offset` 이 어느 글자 기준인지 흐려진다.

좌표가 틀리면 저장 전에 멈추고, 없는 칸과 없는 문단을 **갈라서** 말한다 —
기계가 좌표를 틀리는 길은 그 둘뿐이고, 둘을 뭉쳐 말하면 받는 쪽이 `tables` 를
다시 읽는 것 말고 할 일이 없다.

```
표0 (1,1) 은 문단이 3개다 — 문단9 은 없다
  (문단 번호는 `tables` 의 grid[1][1] 을 줄바꿈으로 나눈 순서다)
```

**자가검증은 또 손댈 데가 없었다.** 기대값 쪽에서 칸 글자를 `\n` 으로 쪼개 그
문단에만 적용하고 다시 이으면 대조가 성립한다 — `lines` 때와 같은 이유다.

화면 편집기는 이 두 연산을 만들지 않는다(칸을 고치면 `SetCell` 이 된다). 그래서
다시하기 로그에는 들어올 길이 없고, `Back` 에 "칸 문단 n 의 m번째부터 k자" 를
더해 두지 않았다 — 쓰이지 않는 셈을 한 벌 더 적으면 두 군데서 세는 꼴이 된다.

### 체크박스 — `checks` 로 찾고 `check` 로 켠다 (사용자 보고 2026-10-29)

> "체크박스를 토글할 방법이 없다 … 제안: `hwp check <파일> 7:3:1` 처럼 그 칸의
> 첫 □만 ☑로 바꾸는 것."

"그 칸의 첫 □" 로는 모자랐다. **실측(실무 문서 14개): 박스가 있는 문서 9개,
`□` 123개 · `☑` 10개 · `☐` 2개. 본문 단락에 62개(단락마다 꼭 1개), 표 칸에
73개. 그리고 박스 든 칸의 절반은 박스가 2~9개다.** 칸만 다루면 절반을 놓치고,
"첫 번째" 로 가리키면 아홉 개 든 칸에서 어느 것인지 말할 수 없다.

그래서 **먼저 어디 있는지 읽는다.**

```bash
echo '{"file":"a.hwp","read":["checks"]}' | hwp api
```
```json
{"kind":"para","at":"0:85","section":0,"para":85,"offset":1,
 "box":"□","checked":false,"label":"유학생 유치 계획"}
{"kind":"cell","at":"0:1:1","table":0,"row":1,"col":1,"cellPara":0,"offset":8,
 "box":"□","checked":false,"label":"원예작물"}
```

`label` 은 다음 박스 전까지의 글자다 — 한 칸에 아홉 개가 있을 때 **사람이
어느 것인지 알아보는 이름**이고, 번호만으로는 못 하는 일이다. 그 좌표를 그대로
돌려보낸다.

```json
{"op":"check","section":0,"para":85,"offset":1}
{"op":"check-in-cell","table":0,"row":1,"col":1,"cellPara":0,"offset":8}
{"op":"check","section":0,"para":85,"offset":1,"checked":false}
```

**맹목적 토글이 아니다**(`checked` 기본 `true`). 토글이면 같은 요청을 두 번 보낸
기계가 칸을 다시 꺼 버리는데, 응답을 못 본 쪽이 다시 보내는 것은 맞는 행동이다.
이미 그 상태면 **아무것도 쓰지 않고** 그렇다고 말한다 — `saved` 가 비어 있어
파일을 건드리지 않았다는 것까지 응답에 있다.

```json
{"op":"check","does":[],"note":"이미 켜져 있다 (☑) — 아무것도 쓰지 않았다"}
```

쓰는 글자는 측정한 것만 둔다 — `□`·`☐` ↔ `☑`. `■`·`▣`·`☒` 는 코퍼스에 **한 번도
나오지 않아서** 넣지 않았다. 쓰이지 않는 글자를 "켜진 칸" 으로 넣어 두면 그
정의가 측정보다 넓어지고, 아닌 것을 켜진 칸으로 읽는 길이 생긴다.

### 넣는 순서가 글자 속성을 가른다 (사용자 보고 2026-10-29, 항목 2의 일부)

> "글자 속성을 고를 수 없다 … 원본 안내문의 속성(117 = 기울임 + 회색 #595959)을
> 물려받아 … 제안: `--char-pr 50` 같은 옵션."

체크박스를 지으면서 이것이 걸렸고, **옵션 없이 해결되는 부분**을 찾았다.

백엔드의 `insert-text --offset N` 은 N 에서 끝나는 **왼쪽 구간**에 붙는다.
서식의 박스는 꾸민 구간의 **첫 글자**인 경우가 많다 —

```
[charPr 234: " "][charPr 266: "□ 유학생 유치 계획"]
```

여기서 먼저 지우고 그 자리에 넣으면 새 글자가 **앞 구간(234)** 의 속성을 받는다.
실측으로 진한 박스가 진하지 않게 됐고, charPrIDRef 가 266 → 234 로 갈려
**색·글꼴·크기까지** 함께 바뀌었다. 증인의 `deco` 로도 보였다 —
`start 1 len 11` 이 `start 2 len 10` 으로 줄었다.

한 칸 뒤(`offset + 1`)에 넣으면 그 구간 **안**이라 266 을 물려받고, 그 다음에
원래 박스를 지운다. 실측으로 hwpx 의 charPrIDRef 가 266 그대로다.

```
넣고-지운 뒤: [('234', [' ']), ('266', ['☑ 유학생 유치 계획'])]
```

**꾸밈이 없는 문서에서는 두 순서가 똑같이 통과한다.** 그래서 합성 코퍼스의
`c03.hwpx` 에 꾸민 구간 안의 박스를 두고
`toggling_a_checkbox_keeps_the_character_formatting_of_that_glyph` 가 지킨다 —
순서를 뒤집으면 깨지는 것을 확인했다.

**이것으로 항목 2 전부가 풀리지는 않는다.** "그 칸의 기존 속성을 물려받아 쓰고
싶다" 는 **이 기법으로 된다**(쓰려는 자리의 글자 하나 뒤에 넣고 그 글자를 지운다).
하지만 "`charPr 50` 을 지정하고 싶다" 와 "빈 칸에 특정 속성으로 쓰고 싶다" 는
안 된다 — 백엔드의 `insert-text` 에 속성 인자가 없고, `apply-char-format` 이
받는 `--props` 는 `{"bold":true}` 꼴이라 **증인이 보는 네 가지(진하게·기울임·
밑줄·취소선)를 넘어서는 것은 우리가 확인할 수 없다.** 색을 넣고 "넣었다" 고
말하려면 그걸 되읽을 길이 있어야 하는데, 증인에게 색이 없다.

### 양식의 안 쓰는 칸을 지운다 — 두 걸음으로 (사용자 보고 2026-10-29)

다른 세션이 **아무 도구 없이** HWPX 양식을 채운 이야기를 들었다. zip 을 풀어
`Contents/section0.xml` 을 고치고, 예시 문구를 실제 값으로 바꾸고, 안 쓰는
부분을 **문단째 지우고**, 예시 이미지를 새 이미지로 갈고, mimetype 을 무압축
선두에 두고 다시 묶었다. 잘 됐다.

**그 일 중 둘을 우리 도구로 할 수 없었다.** 문단째 지우기(개체가 달려 있으면
거부했다)와 그림 교체. 그래서 같은 일이 **세 번째로** 일어났다 —

| | 우리 구멍 | 사용자가 간 길 |
|---|---|---|
| 1 | `set-cell` 이 한 줄만 받았다 | XML 직접 수정 |
| 2 | 칸 안 문단에 좌표가 없었다 | XML `subList` 직접 교체 |
| 3 | 개체 달린 단락을 못 지웠다 | **zip 풀어 XML 직접 수정** |

전부 **도구의 구멍이 사용자를 자가검증 없는 경로로 밀어낸 것**이다. 특히 3번의
거부는 내가 원칙으로 세운 규칙이었다 — "개체를 만들 수 없으니 *그렇게 되어야
한다* 를 쓸 수 없고, 그러면 검증 없는 쓰기다". 원칙은 맞았고 **결과는 검증이
0인 경로**였다.

#### 재 보니 표는 쓸 수 있었다

```json
{"op":"delete-table","table":2}
{"op":"delete-para","section":0,"para":5}
```

`delete-table` 뒤에 **빈 단락이 남고**, 그 단락은 이제 평범하게 지울 수 있다
(개체가 있는 동안은 여전히 거부된다). 그림·글상자는 `delete-control` 로 개체만
빼고 같은 두 걸음을 간다. 네 걸음 다 자가검증을 지난다.

실측(s03.hwpx, 표 13개): 표 13 → 12, 뒤 번호가 당겨지고(t3 → t2), **본문 단락
수는 60 → 60**, 단락 글자는 하나도 안 바뀐다.

#### 자가검증이 내 기대값을 먼저 잡았다

처음에 "표를 지우면 단락도 같이 빠진다" 로 짰다. `read:["text"]` 의 `body` 가
73 → 72 로 줄어든 것을 보고 그렇게 읽었는데, 그 하나는 단락이 아니라 `body`
안의 **표 항목**이었다. 틀린 기대값으로 저장을 걸었고 —

```
저장을 멈췄습니다 — 저장본이 기대와 다릅니다. 원본은 그대로 두었습니다.
  본문 단락 수: 기대 59 / 실제 60
  구역0 단락14 의 개체 수가 다릅니다 — 기대 1 / 실제 0
```

파일은 안 바뀌었다. **넣을 때는 표와 단락이 함께 들어오고, 지울 때는 표만
나간다** — 그 비대칭을 모르고 짠 것이고, 막으려던 종류의 틀림이 정확히 이것이다.

#### 거부는 남기되 갈 곳을 말한다

전 메시지는 "개체를 만들거나 옮기지 못해서 결과를 검증할 수 없다" 로 끝났다.
맞는 말이지만 **받는 쪽이 할 수 있는 일이 없다** — 그래서 도구 밖으로 나갔다.
지금은 이렇게 말한다.

```
구역0 단락5 에는 그리기개체(표·그림·글상자)가 1개 달려 있어 단락째 지울 수
없습니다. 개체를 먼저 빼면 됩니다 — 표면 `delete-table`, 그림·글상자면
`delete-control` 로 개체를 빼고 남은 빈 단락을 지우세요.
```

`delete-control` 에 표 든 단락을 주면 거부하고 `delete-table` 로 보낸다. 개체
번호만으로는 표인지 그림인지 알 수 없고, 표를 그쪽으로 지우면 **칸이 남은
기대값**이 만들어져 저장이 "표0 의 글자가 다르다" 로 멈춘다 — 엉뚱한 말이다.

#### 아직 못 하는 것 — 그림 교체

양식의 예시 이미지를 새 이미지로 **바꾸는** 명령이 백엔드에 없다
(`insert-image` 는 넣기뿐이다). 우리가 BinData 를 직접 갈면 그게 바로 그 Python
경로이고, **우리도 검증할 수 없다.** 상류(`rhwp`, MIT)에 요청할 일이다.

그리고 `.hwp`(구형 이진 포맷)에서는 그 Python 경로가 **아예 시작되지 않는다** —
CFB 컨테이너 + 스트림별 raw deflate + 태그 레코드라서 zip 처럼 풀 수 없다.

### 변환 — 백엔드에 있고, 우리는 안 내놨다. 그 답을 재다가 결함이 나왔다

사용자 질문(2026-10-30): "hwp → hwpx 변환 기능 같은 게 있나?"

백엔드에는 **양방향 다** 있다. 우리는 **내놓지 않았다** — `output` 의 확장자가
원본과 다르면 거부하고 `rhwp` 를 직접 쓰라고 말한다.

```bash
rhwp export-hwpx <입력.hwp|hwpx> [출력.hwpx] [--verify]   # → HWPX
rhwp convert     <입력.hwp|hwpx>  <출력.hwp>  [--verify]   # → HWP5
```

#### 무손실인가 — 증인으로 쟀다

`--verify` 는 백엔드가 자기 산출물을 자기가 다시 파싱해 보는 것이다. **작성자가
자기 답을 채점하는 것**이므로(`scaffold` 때와 같은 이유) 우리 독립 증인으로
글자·칸·그림·꾸밈을 대조했다. 실무 문서 10개(hwp 5 + hwpx 5), 양방향.

결과: **무손실이다.** 단락 글자·표 칸·표 수·그림 수·글자별 꾸밈이 전부 같다.

꾸밈은 **글자별로** 비교해야 한다. 꾸밈 구간의 경계가 갈리는 경우가 있는데
(27구간 → 27구간인데 경계가 다름) 글자마다의 진하게·기울임·밑줄·취소선은
같다. 비교 단위를 구간으로 잡으면 손실이 아닌 것을 손실로 읽는다.

본문도 **보이는 글자로** 비교해야 한다. 날 글자로는 다르게 나오는데, 두 포맷이
**개체 자리 표시의 수가 다르기** 때문이다(p.hwpx 단락0 은 HWP5 쪽에 U+FFFC 가
3개 더 있다 — 구역 정의·쪽번호 같은 확장 컨트롤이고 OWPML 은 본문 글자로
내지 않는다).

#### 그런데 처음 쟀을 때 "본문이 다르다" 가 나왔다 — 범인은 우리였다

HWPX → HWP 왕복에서 문서 5개 중 3개의 본문이 다르게 읽혔다. 변환이 줄바꿈을
잃는 줄 알았다. **아니었다.**

```
전: …'추진 계획과 연차별 목표\n- 세부 과제 '
후: …'추진 계획과 연차별 목표- 세부 과제 '
```

모든 차이가 **U+000A 하나**였고, 우리 HWP5 판독기가 단독 컨트롤 10(강제
줄바꿈)을 **버리고** 있었다. OWPML 쪽은 `hp:lineBreak` 를 `'\n'` 으로 읽는데
HWP5 쪽에서 버린 것 — **같은 개념을 두 판독기가 다르게 읽었다.** U+2007
(컨트롤 30·31 ↔ `hp:fwSpace`) 때와 같은 함수, 같은 모양이다.

10 을 `'\n'` 으로 읽게 하니 왕복 차이가 **5/5 전부 0** 이 됐다. 줄바꿈은
`.hwp` 안에 있었다.

#### 글자 하나가 빠지는 데서 끝나지 않는다

백엔드의 `--offset` 은 그 글자를 **센다.** 실측으로 확인했다 — 줄바꿈이
64번째인 단락의 65번째에 넣으면 줄바꿈 **바로 뒤**에 들어간다.

```
전: …'추진 계획과 연차별 목표\n- 세부 과제 셋으로 '
후: …'추진 계획과 연차별 목표\n◆- 세부 과제 셋으로'   ← offset 65 에 넣은 것
```

그러니 버리는 동안 **강제 줄바꿈이 있는 `.hwp` 의 모든 오프셋이 하나씩 짧았다.**
편집이 엉뚱한 자리에 들어간다.

**그리고 자가검증은 이걸 못 잡는다** — 기대값과 재생이 같은 틀린 오프셋을 쓰므로
둘이 일치해 통과한다. 접힌 줄 결함과 **정확히 같은 종류**이고, 이중 검증이
막아 주는 부류가 아니다.

#### 왜 시험이 안 잡았나 — 그리고 시험을 어디에 뒀나

코퍼스의 `.hwp` 5개에 강제 줄바꿈이 **없다.** 줄바꿈이 있는 문서는 `.hwpx`
쪽이고, 두 포맷을 대조하는 기존 시험은 `.hwp` → `.hwpx` 방향만 봤다.

`the_two_formats_read_the_same_text_including_forced_line_breaks` 를 두었고
되돌려 무는 것을 확인했다. **실무 문서 전용**이다 — 합성 코퍼스에는 강제
줄바꿈을 넣을 수가 없다(백엔드의 `insert-text --text` 가 줄바꿈을 거부한다).
그래서 꺼지는 관문 수를 20 → **21** 로 다시 선언했고, MANIFEST 의 "못 덮는 것"
에 적었다. 그리고 이 시험은 **줄바꿈을 하나도 못 봤으면 실패한다** — 조용히
통과하는 쪽이 더 나쁘다.

### `hwp convert` — 내놓았다. 증인이 대조한 뒤에만 파일을 남긴다

```bash
hwp convert 양식.hwp 양식.hwpx            # 방향은 목적지 확장자가 정한다
hwp convert 양식.hwp 양식.hwpx --dry-run  # 무엇을 대조할지만 말한다
echo '{"file":"양식.hwp","convert":true,"output":"양식.hwpx"}' | hwp api
```

대조하는 축은 **재서 고른 다섯 개**다. 포맷 간에 뜻이 같은 것만 넣었다 —
아무거나 비교하면 손실이 아닌 것이 손실로 잡힌다.

1. 본문 단락 글자 — **보이는 글자로**(`offset::visible`)
2. **글자별** 꾸밈 (구간 경계는 포맷에 따라 갈린다)
3. 표 칸 글자 — `(표, 행, 열)` 마다
4. 표의 꼴 — 번호마다의 행·열
5. 그림이 올라앉은 단락과 그 수 — **자리까지**

비교하지 않는 것도 적어 둔다: 날 글자(개체 자리 표시 U+FFFC 수가 포맷마다
다르다), 꾸밈 구간의 경계, 컨테이너 부품 수(ZIP 12 ↔ CFB 11 은 애초에 다른
것이다). 표의 **앵커**도 넣지 않았다 — 증인이 모르고, 백엔드에게 물으면
**백엔드가 자기 산출물을 자기 값으로 채점하는** 꼴이 된다.

#### 막지 않는 차이는 경고로 낸다

강제 줄바꿈의 **글자 속성**이 변환에서 바뀐다(실측: HWPX 는 그 줄바꿈이 진한
구간 안인데 HWP5 쪽에는 그 구간이 없다). 보이는 글자는 그대로다 — 줄바꿈은
글자를 그리지 않는다. 그렇다고 걸러내지는 않았다. **이 저장소의 1번 재발
패턴이 "시험을 깔끔하게 하려고 걸러낸 것이 결함이 사는 자리"** 이고, 게다가
보이지 않는다는 말도 반쪽이다 — 백엔드의 `insert-text` 는 왼쪽 구간의 속성을
물려주므로 그 줄바꿈 **바로 뒤**에 글자를 넣으면 물려받는 속성이 달라진다.

그래서 등급을 나눈다. 보이는 글자가 달라지면 **멈추고**, 줄바꿈 자리만
달라지면 **파일을 내놓고 말한다.**

```
/tmp/cv.hwp 로 바꿨습니다 (hwp)
  증인이 대조했습니다 — 본문 36단락 · 표 칸 40개 · 그림 2개
  ⚠ 강제 줄바꿈 1곳의 글자 속성이 바뀌었습니다 — 보이는 글자는 그대로입니다.
    다만 그 줄바꿈 바로 뒤에 글자를 넣으면 물려받는 속성이 달라집니다
```

`hwp api` 는 같은 것을 `warnings` 로 받는다 — 사람만 보고 기계가 못 받으면
같은 기능이 아니다.

### 변환을 지으니 판독기 결함이 **네 개** 나왔다

변환은 두 판독기가 **같은 문서를 각자 읽어 맞대는** 일이다. 그래서 둘이
갈라진 자리가 전부 드러났다. 다 같은 모양이다 — **같은 개념을 두 판독기가
다르게 읽는다.**

| | 결함 | 어떻게 드러났나 |
|---|---|---|
| 1 | HWP5 가 강제 줄바꿈(컨트롤 10)을 **버린다** | 왕복에서 본문이 달라졌다 |
| 2 | 구간 위치 환산이 1번과 **갈라졌다** | 줄바꿈 뒤 꾸밈이 한 칸 밀렸다 |
| 3 | OWPML 이 칸의 **꼬리 빈 단락을 떼지 않는다** | 같은 칸이 포맷마다 달랐다 |
| 4 | 양쪽 판독기가 칸 안 **글상자 글자를 칸으로 끌어온다** | 1×1 칸이 `①⏎②` 로 읽혔다 |

2번은 `raw_positions` 와 `decode_para_text` 가 쌍둥이인데 한쪽만 고쳐서
생겼다. 그 함수 주석에 **"두 함수가 갈라지면 구간이 엉뚱한 글자에 붙는다"**
고 적혀 있었다 — 경고를 적어 두고 내가 그걸 어겼다.

4번이 가장 깊었다. HWP5 레코드에는 **중첩 수준**이 있는데 칸을 읽는 두 루프가
그걸 `_` 로 버리고 있었다. 글상자 안의 글자 목록이 `(행 0, 열 0)` 으로 또
나타나 1×1 표의 좌표 검사를 통과해 칸을 덮었다. 수준을 보게 고쳤고, **짐작한
규칙이 두 번 틀려 시험 넷을 깼다** — 실측으로 정했다: `TABLE` 과 그 칸의
`LIST_HEADER` 는 **같은 수준**이고(둘 다 2) `PARA_TEXT` 가 한 단계 아래다.
`PARA_HEADER` 도 `LIST_HEADER` 와 형제다. 이 포맷은 "담는 것" 과 "담기는 것"
을 수준으로 가르지 않는 자리가 있다.

그리고 중첩 표가 끝나면 **바깥 표의 칸이 또 나오므로** 마지막 표만 보면 안
된다 — 표를 스택으로 든다.

**4번은 보기만 이상한 게 아니다.** `edit::snapshot` 이 칸 글자를 쓰므로, 글상자
가 든 칸은 `set-cell` 의 기대값이 영원히 어긋나 **저장이 되지 않았다.**

### 커서가 글자 위에 서지 않았다 — 접는 쪽이 자리를 안 알려 줬다

`wrap()` 은 줄을 **문자열로만** 돌려줬다. 그러면 **끊은 자리에서 버린 글자가
어디였는지 아무도 모른다.** 접는 쪽은 줄 끝 공백을 버리는데(표시로는 맞다 —
줄 끝에 남기면 복사할 때 따라간다), 커서를 놓는 쪽은 **줄들의 글자 수 합이
원문 길이와 같다고 가정**하고 있었다.

```
접은 줄 4개의 글자 합 77 vs 원문 80 — 차이 3
```

끊은 자리마다 하나씩 모자라므로, 커서가 **지나온 접힘 수만큼 오른쪽으로 밀려**
그려졌다. 단락 끝 쪽 오프셋은 아예 못 찾아 마지막 줄의 **0열로 떨어졌다** —
뒤로 갈수록 커서가 앞으로 되돌아가는 꼴이다.

#### 경계를 글자 오프셋으로 내보낸다

```rust
pub struct Span {
    pub text: String,
    /// 원문에서 이 줄이 시작하는 **글자** 번째
    pub start: usize,
    /// 이 줄이 담은 글자 수. **버린 공백·줄바꿈은 들어가지 않는다** —
    /// 그래서 `start + len` 이 다음 줄의 `start` 와 다를 수 있고,
    /// 그 틈이 바로 버린 글자다.
    pub len: usize,
}
```

`wrap()` 은 `wrap_spans()` 위에 남겨 뒀다(그릴 줄만 필요한 자리가 많다).
`cursor_screen` 은 이제 그 자리를 받아 쓰므로 **더해 가며 찾지 않는다.**
커서가 버린 글자 자리에 있으면 앞 줄의 끝에 둔다 — 그 글자는 어느 줄에도
그려지지 않으니까.

#### 같은 뿌리의 둘째 — 강제 줄바꿈에서 줄을 바꾼다

`wrap()` 이 문단 안의 `'\n'` 을 무시해서 `연차별 목표- 세부 과제` 처럼 붙어
보였다. **문서가 거기서 줄을 바꾸라고 말한 것**인데 화면이 안 바꿨다.

```
   2   ○ 여름철 고온 대응 관수 기술을 적용한 노지 재배 안정성 향상 융합
           과제의 세부 추진 계획과 연차별 목표
           - 세부 과제 셋으로 나누어 추진
```

#### 무는 시험 — 불변식으로 적었다

`접은_줄은_원문의_그_자리를_가리킨다` 가 폭 5가지 × 글 6가지에 대해 넷을 본다:
줄의 글자가 원문의 그 자리와 같은가, 자리가 앞으로만 가는가, 마지막 줄이 원문
끝에 닿는가, **버린 글자가 공백이나 줄바꿈뿐인가**(글자를 잃지 않는가).

`접힌_단락에서_커서가_글자_위에_선다` 는 모든 오프셋에 대해 커서가 되돌아가지
않고 그 자리에 그려지는 글자가 그 오프셋의 글자인지 본다. 옛 셈으로 되돌리면
**오프셋 25**(첫 접힘 바로 뒤)에서 깨진다.

### 글자 꾸밈을 건다 — 그리고 되읽어 확인한다 (hwp-vi#5)

사용자 보고: 읽기에는 `deco` 가 있는데 쓰기가 없었다 — "읽어서 알 수 있는데
만들 수 없으면, AI 가 문서를 고칠 수는 있어도 쓸 수는 없다".

```json
{"op":"set-deco","section":0,"para":3,"offset":3,"count":5,
 "bold":true,"underline":true}
```

구간은 `read:["deco"]` 가 주는 좌표와 같다. `false` 로 **끈다.**

#### 받는 키는 셋뿐이다 — 실측으로 정했다

백엔드의 `apply-char-format` 은 `--props` 의 **모르는 키를 조용히 무시하고
성공을 보고한다**(`boldd` 로 확인 — `apply-para-format` 때와 같은 함정이다).
그래서 "듣는 키" 를 되읽어 가려냈다.

| 준 것 | 결과 |
|---|---|
| `bold`·`italic`·`underline` 에 `true`/`false` | **듣는다** (켜고 끄기 둘 다) |
| `underline: "SOLID"` (글자) | 아무 일도 안 일어난다 |
| `strikeout`·`strike` (무엇을 줘도) | **아무 일도 안 일어난다** |

그래서 취소선은 받지 않는다. 다만 **칸은 두고 이유를 말하며 거부한다** —
serde 가 "모르는 칸" 으로 끝내면 받는 쪽은 왜인지 모르고 오타인 줄 알고 다시
보낸다.

#### 자가검증에 꾸밈을 넣었다 — 이게 이 작업의 본체다

되읽어 대조하지 않으면 `set-deco` 가 백엔드의 조용한 무시를 **그대로
물려받는다.** 그래서 `Snapshot` 에 **글자마다의 꾸밈 표**(`B`·`I`·`U`·`S`)를
담았다. 구간이 아니라 글자별인 이유는 변환을 재면서 배웠다 — 구간 경계는
포맷·판에 따라 갈리는데 글자마다의 속성은 갈리지 않는다.

일부러 키를 틀려 보니 **저장이 멈췄다.**

```
저장을 멈췄습니다 — 저장본이 기대와 다릅니다. 원본은 그대로 두었습니다.
  구역0 단락3 의 글자 꾸밈이 다릅니다 — 3번째 글자: 기대 "B" / 실제 "없음"
```

#### 대조 범위를 좁힌 이유, 그리고 남는 구멍

꾸밈은 **우리가 바꾸겠다고 말한 단락만** 비교한다(`deco_checked`). 글자를
고치는 연산도 꾸밈을 바꾸기 때문이다 — 넣은 글자는 **왼쪽 구간의 속성을
물려받는다**(체크박스 작업에서 실측). 그 셈을 모든 연산에 모델링하면 틀릴
자리가 많고, 틀리면 꾸밈이 있는 문서의 저장이 **전부** 막힌다.

그래서 글자를 고치는 연산은 그 단락의 꾸밈 예측을 **버리고**(모르는 것을
안다고 하지 않는다), 단락을 넣고 빼는 연산은 좌표가 밀리므로 전부 버린다.

**남는 구멍**: 글자를 고치는 연산이 **다른 곳의** 꾸밈을 조용히 바꾸는 경우는
여전히 안 잡힌다. 적어 두고 다음에 본다 — 가려 두는 것보다 적어 두는 쪽이
낫다.

### 규격이 정해진 문서를 만든다 — 우리가 XML 을 적고 증인이 확인한다

사용자 보고(hwp-vi#4): `create` 로는 글자 크기·여백을 지정할 수 없었다.

> A4규격: 글자 13포인트, 줄 간격 160%, 상하여백 15, 좌우여백 25

그리고 그 서식은 **원고 A4 매당 정산**이다. 10pt·여백 30mm 로 나오면 같은 글이
더 적은 쪽에 담기므로 **서식 위반이자 정산 근거의 소실**이다.

```json
{"create":{"version":"1","title":"교과목 개발 원고","font":"함초롬바탕",
  "font_size_pt":13,
  "margins_mm":{"top":15,"bottom":15,"left":25,"right":25},
  "blocks":[…]},
 "output":"원고.hwpx"}
```

백엔드의 `scaffold` 는 그 칸을 받지 않으므로 **우리가 HWPX 의 XML 을 적는다.**
명세에서 그 둘만 떼어 내 넘기고(모르는 칸은 백엔드가 거부한다 — 그게 맞다),
만든 뒤 고친다.

#### "charPr 0 이 본문" 을 코드에 박지 않았다

생성물을 재 보면 `charPr 0`=본문 10pt, `1`=제목 18pt, `2`=머리글 12pt 이고
명세를 바꿔도 그대로다. 그래도 박지 않았다 — 그건 **백엔드 생성물의 성질**이고
판이 바뀌면 조용히 틀린다. 대신 **본문 글줄의 글자로 찾아** 그 문단이 가리키는
`charPrIDRef` 를 모은다. 그러면 가정이 필요 없다.

#### 되읽어 대조한다 — 이것이 "읽을 수 있는 것만 쓴다" 의 값이다

우리가 적은 수도 백엔드가 적은 것과 **같은 관문**을 지난다. 증인이 글자 크기와
쪽 설정을 읽으므로(앞 절), 요청한 값이 실제로 들어갔는지 확인할 수 있다.

```
여백: 좌25.0 우25.0 상15.0 하15.0 mm
단락0 18.0pt '교과목 개발 원고'      ← 제목은 안 건드린다
단락1 12.0pt '1. 개요'               ← 머리글도
단락2 13.0pt ' ○ 본 원고는 규격에 맞춰 작성한다.'
단락3 13.0pt ' ○ 쪽수가 정산 근거이므로 조판이 중요하다.'
```

쓰는 쪽을 일부러 망가뜨리니 **거부하고 파일을 남기지 않았다** —
`본문 글자 크기가 다릅니다 — 요청 13.0pt / 만들어진 것 [9.99]pt`.

#### 세 가지를 더 확인했다

- **백엔드가 받는다.** 우리가 다시 묶은 ZIP 이므로 이게 관문이다 —
  `rhwp convert --verify` 가 "IR 차이 없음" 이라고 한다. `mimetype` 을 맨 앞에
  무압축으로 두지 않으면 한글이 못 여는데, 한글은 여기서 띄울 수 없으니
  백엔드의 수락이 가장 가까운 확인이다.
- **변환해도 수가 남는다.** `.hwp` 로 바꿔도 25mm·13pt 다 — 제출은 `.hwp` 로
  하는 일이 많다.
- **받지 않는 값은 거부한다.** `font_size_pt: 999`, `margins_mm: {middle: 10}`.

### 유출 관문이 나를 잡았다 — 그리고 한계도 드러났다

이 작업을 올리려는데 동기화가 멈췄다.

```
✗ 허용되지 않은 문구 1건 — 동기화를 멈춥니다
    crates/hwp-core/src/wrap.rs: '○ 극한기후 대응 AI 기술을 적용한 …'
```

`wrap()` 시험 자료로 **실무 문서의 한 문장을 그대로 썼다.** 관문이 있는 이유가
정확히 이것이고, 공개 나무는 안 바뀌었다. 허용 목록에 넣는 것이 아니라 문장을
지어 썼다.

그리고 두 가지가 더 드러났다.

**1) 공백이 다르면 통과했다.** 같은 문장을 다른 파일에서는 소스에서 줄을 이어
적어 공백이 여러 칸이 됐고, 글자열이 정확히 맞지 않아 **통과했다.** 사람 눈에는
같은 문장이다. 관문이 공백을 무지르고 비교하게 고쳤더니 — **README 에서 또
잡았다.** 어제 결함을 설명하며 그 문장을 인용해 뒀다.

**2) 통째 복사는 잡고 발췌는 못 잡는다.** 고친 뒤에도 한 줄이 남았는데
걸리지 않았다. 문서 조각은 `- … 기술 개발 및 개발된 기술의 빠른 적용 필요`
인데 README 에는 **앞 절반만** 적혀 있었다. 관문은 "문서의 조각이 공개 파일
안에 있는가" 를 보므로 발췌는 빠져나간다.

n-gram 겹침으로 넓히면 공문서 상투구에서 거짓 양성이 쏟아져 **사람이 관문을
끄게 된다** — 끈 관문은 없는 관문이다. 그래서 넓히지 않고 한계를 스크립트에
적어 뒀다. 1차 방어는 **실무 문서의 문장을 예시로 쓰지 않는 것**이다.

### 쓰려면 먼저 읽어야 한다 — 증인에 글자 크기와 쪽 설정을 넣었다

사용자 질문: "rhwp 에 꼭 의존해야 하나." 재 보니 **쓰기는 HWPX 에서 우리가 할
수 있다** — 생성물의 XML 을 손으로 고쳐(본문 10pt → 13pt, 좌우 30mm → 25mm)
`mimetype` 무압축 선두로 다시 묶었더니 **양쪽 판독기가 다 받고 글자도 그대로**
였다. 그러니 "상류 작업" 이라고 적어 둔 것들은 포맷의 제약이 아니라 **백엔드를
유일한 작성자로 둔 결과**다.

다만 순서가 있다. **읽지 못하는 것은 쓰지 않는다** — 쓴 것을 되읽어 대조하는
것이 이 도구의 전부이므로, 증인이 읽는 것만 쓸 수 있다. 그래서 읽기를 먼저
늘렸다.

```bash
echo '{"file":"양식.hwp","read":["page"]}' | hwp api
```
```json
{"widthMm":210.0,"heightMm":297.0,
 "marginMm":{"left":20.0,"right":20.0,"top":12.3,"bottom":10.0,…},
 "hwpunit":{"width":59528,"height":84188,"left":5669,…}}
```

`read:["deco"]` 의 구간마다 `sizePt` 가 붙는다. mm 와 HWPUNIT 을 둘 다 주는
것은 **사람은 mm 로 말하고 쓰는 쪽은 HWPUNIT 으로 말하기** 때문이다.

#### 자리는 짐작하지 않고 변환으로 확정했다

HWP5 는 레코드의 **바이트 자리**를 알아야 읽을 수 있다. 이 세션에서 짐작으로
두 번 틀려 시험 넷을 깼으므로(표와 칸의 중첩 수준), 이번에는 **변환을 측정
도구로** 썼다 — 변환된 HWPX 는 속성 이름이 분명하니 그 값과 맞는 자리를 찾으면
된다.

| 확정한 것 | 자리 | 단위 | 어떻게 확인했나 |
|---|---|---|---|
| 글자 크기 | `CHAR_SHAPE[42..46]` INT32 | 1/100 pt | s00.hwp 306개가 변환본 `hh:charPr/@height` 와 **순서까지** 같다 |
| 쪽 설정 | `PAGE_DEF`(태그 `BEGIN+57`) 앞 9개 UINT32 | HWPUNIT | `59528 84188 5669 5669 3500 2834 3000 1354 0` 이 변환본 `hp:pagePr`·`hp:margin` 과 같다 |

`CHAR_SHAPE` 의 레이아웃도 맞아떨어진다: faceNameIds 7×2 + ratios 7 +
spacings 7 + relSizes 7 + offsets 7 = **42**, 그 다음이 크기, 그 다음이 속성
(우리가 이미 `[46..50]` 에서 읽던 그 자리다).

그 측정을 **관문으로 굳혔다** — `the_two_formats_agree_on_char_size_and_page_setup`
은 자리를 4바이트만 밀어도 깨진다.

#### 구간이 꾸밈만 들지 않는다

전에는 꾸밈 없는 구간을 버렸다(`deco.any()`). 그러면 "13pt 로 썼다" 를 되읽을
수가 없다. 지금은 **꾸밈이나 크기 중 하나라도 있으면** 담고, 합치는 기준에도
크기를 넣었다 — 꾸밈만 보면 12pt 와 13pt 구간이 한 구간으로 뭉개진다.

시험의 요구도 같이 고쳤다. `decoration_runs_stay_inside_their_paragraph` 가
"꾸밈 없는 구간이 담겼다" 를 문제로 적어 뒀는데, 그건 구간이 꾸밈만 들던 때의
말이다. 요구의 **뜻**(아무것도 말하지 않는 구간을 내보내지 않는다)은 그대로
두고 조건만 넓혔다.

#### 그래서 rhwp 와의 관계

버리지 않는다. **천장으로 두지 않는다.**

| | 누가 |
|---|---|
| 조판 — 쪽나눔·줄 분할·단 폭 (`dump-pages`) | **rhwp.** 대안이 없다 |
| `.hwp` 쓰기 (CFB + 스트림별 deflate) | **rhwp** |
| 변환 | **rhwp** (무손실 확인) |
| HWPX 의 서식·여백·글자 크기 | **우리** — 백엔드가 안 받는 것들 |
| 검증 | **증인.** 늘 우리 |

그리고 **잃는 것도 적어 둔다.** 지금은 세 쪽이다 — 우리가 계산한 기대값,
rhwp 가 쓴 결과, 우리 증인이 되읽은 값. 우리가 직접 쓰면 두 쪽이 되고,
**포맷을 잘못 이해한 버그는 쓰는 쪽과 읽는 쪽이 똑같이 틀리므로 양쪽을
통과한다**(접힌 줄 결함, 컨트롤 10 결함이 그 모양이었다). 제3자가 쓰는 것이
그 구멍을 메우고 있었다. 그래서 우리가 쓰는 범위는 **백엔드가 못 하는 것**으로
한정하고, 할 수 있는 것은 계속 백엔드에 맡긴다.

### U+2028 은 거부한다 (사용자 질문 2026-10-29)

> "참고: U+2028 은 통과해서 저장됩니다. 하지만 `cells` 보기에서는 공백으로
> 나오고 한글에서 줄바꿈으로 보이는지 확인되지 않아 쓰지 않았습니다.
> **받아들이든 거부하든 한쪽으로 정하는 게 나아 보입니다.**"

거부로 정했다. 실측하니 저장은 되는데 응답의 `changed[].after` 는 **공백**으로
보고하고 파일에는 U+2028 이 들어 있다 — 미리보기와 파일이 어긋나는 상태이고, 이
도구에서 가장 비싼 종류의 틀림이다. 한글이 그걸 줄바꿈으로 그리는지도 확인되지
않았으므로, "통과시키고 어떻게 보이는지는 사용자가 알아서" 는 답이 아니다.
문단을 나누는 **확인된 길**(`lines`)이 생긴 뒤이므로 거부해도 막히는 일이 없다.

U+2028·U+2029·U+0085·탭·제어문자를 `text`·`lines`·`set-para` 전부에서 거부한다
(한 군데만 막으면 다른 쪽으로 샌다). 몇 번째 글자가 걸렸는지와 **갈 곳**을
같이 말한다.


사용자 요청: "AI 가 HWP 파일을 만들고 수정하고 저장하기 편하게." 고치기와 저장은
있었고 **만들기가 비어 있었다** — 기계 쪽에 `create` 가 없어서 AI 는 이미 있는
문서만 손댈 수 있었다.

```bash
# 만들기 — 미리보기는 디스크를 건드리지 않는다
echo '{"create":{…},"output":"새문서.hwpx","dryRun":true}' | hwp api
echo '{"create":{…},"output":"새문서.hwpx"}'               | hwp api
# 고치기 → 저장 (한 요청에 섞이고 한 번만 저장된다)
echo '{"file":"새문서.hwpx","ops":[{"op":"set-cell",…}]}'   | hwp api
# 읽기 — 모든 항목이 편집 좌표를 들고 있다
echo '{"file":"새문서.hwpx","read":["text","tables"]}'      | hwp api
```

명세는 백엔드가 받는 그대로다 — `version`·`title`·`font`·`page_size`(`width_mm`/
`height_mm`)·`blocks`. 블록은 `heading`·`paragraph`·`table` 셋, `cell_align` 은
`justify|left|center|right`. **우리가 베껴 적지 않고 그대로 넘긴다**(적으면
백엔드가 늘 때 어긋난다).

### 만들기도 자가검증을 지난다

백엔드의 `scaffold` 를 그냥 통과시키면 이 프로젝트의 중심 장치가 만들기에만
빠진다. `scaffold` 는 자기가 만든 것을 자기가 세어 `blockCount`·`tableCount` 로
보고하는데, **그건 작성자가 자기 답을 채점하는 것**이다. 그래서 저장과 같은
모양으로 간다 — 명세에서 "이렇게 되어야 한다"(글줄마다의 글자, 표마다의 칸)를
뽑고, 임시본을 만들고, **증인으로 다시 읽어** 대조하고, 같을 때만 `rename` 으로
들여놓는다. 응답의 수는 그래서 `"verifiedBy": "witness"` 다.

무는지 확인했다: 백엔드에 일부러 다른 명세를 보내니 `만들기를 멈췄습니다 —
만든 문서가 명세와 다릅니다` 로 멈추고 파일도 임시본도 남지 않았다.

### 쓰기가 남의 문서를 지우던 네 길을 막았다

감사가 찾은 것이고, AI 는 사람보다 빠르고 많이 호출하니 이 경로를 가장 세게
밟는다. **인터페이스를 얹기 전에 먼저 고쳤다.**

| 무엇이 | 어떻게 고쳤나 |
|---|---|
| `dryRun`+`output` 이 목적지를 파괴 | `dry_run` 검사를 `fs::copy` **앞으로**. 미리보기는 원본에서 읽는다 |
| `output` 이 있는 파일을 말없이 덮음 | 거부하고 `"overwrite": true` 를 요구한다 (사람 쪽 `!` 와 같은 규칙) |
| 하드링크 목적지 → 0바이트 | `same_file` 을 **inode 비교**로. `canonicalize` 는 하드링크를 못 본다 |
| `save_as` 가 목적지를 검증 전에 덮음 | 목적지 **옆의 임시본**에서 끝내고 `rename`. 실패하면 목적지 무변경 |

곁들여 저장 경로 셋도 고쳤다 — 마지막 교체를 `O_TRUNC` 복사에서 **`rename`** 으로
(끊기면 0바이트가 남았다), **권한 보존**(600 문서가 664 가 됐다), `.bak` 을
덮지 않고 **세대로**(두 번 저장하면 원본이 영구히 사라졌다).

### 기계가 걸려 넘어지던 계약 결함 일곱

| | 전 | 후 |
|---|---|---|
| `insert-table`·`create` | 동작하는데 `--capabilities` 에 **없다** | 올렸고, 빠지면 시험이 문다 |
| 모르는 `read` 이름 | `ok:true` + 빈 응답 → "표가 없다"로 오독 | 거부하고 받는 이름을 말한다 |
| `find` | 단락당 **첫 일치만** | 모든 일치 (15 → 19 hit) |
| 오류 봉투 | `schemaVersion` 없음 | 세 봉투를 한 함수로 모아 넣는다 |
| `untrusted` 표지 | `find`·`frame`·`ops` 응답에 **없음** | 끝에서 한 번, 응답에 **실제로 있는 칸만** 가리킨다 |
| `read:["text"]` 의 `ref` | 찾아갈 `tables` 가 없다 | `ref` 가 있으면 `tables` 도 싣는다 |
| 비UTF-8 stdin | stdout 이 비고 평문이 stderr 로 | JSON 봉투로 나온다 |

**자기서술은 손으로 적는 목록이라 빠진다.** `insert-table` 이 그렇게 빠졌고,
"컴파일러가 같음을 강제한다"는 장치는 `Action` 변종만 보므로 알려 주지
않았다 — 메뉴의 `Prompt` 가 셋으로 늘어난 것도 못 잡아서 "표 만들기" 가
`save-as` 로 보고됐다. 지금은 `OpSpec` 이 받는 이름을 세어 `CAPS` 와 맞추는
시험이 있고, 되돌려 무는 것을 확인했다.

### 기계가 잡아 주는 것

| | 결과 |
|---|---|

### 고친 것 — 프로즈에 제어 흐름이 매달려 있었다

`ZZ`(저장하고 나가기)가 나갈지를 **상태줄 문구에 "멈췄" 가 들어 있는지**로
정하고 있었다.

```rust
write_file(app);
if !app.message.contains("멈췄") { app.quit = true; }   // 전
if write_file(app) { app.quit = true; }                 // 후
```

저장 성공 여부를 **사람에게 보여 줄 말**에 매달아 둔 것이다. 같은 날 말투를
일괄로 고쳤는데("저장을 멈췄다" → "저장을 **멈췄**습니다") **어간이 우연히 같아서
살았다.** "중단했습니다" 로 썼다면 `ZZ` 가 저장 실패를 모른 채 나가 쌓인 편집이
사라졌을 것이다.

**정직하게**: 이것이 당시 실제로 깨져 있었다고 먼저 말했는데 **틀렸다.** 재현
시험을 써 보니 통과했다 — 텍스트 경로의 모든 오류는 `match saved` 의 Err 가지를
지나며 "멈췄습니다" 접두사를 받는다. 그 검사를 지나지 않는 경로는 핀 오류와
백엔드 없음 둘뿐이고, 둘 다 **세션 중에 백엔드가 사라져야** 닿는다. 그러니
등급은 "살아 있는 데이터 손실" 이 아니라 **"구조상 깨지기 쉬움"** 이다. 고친
이유는 그것으로 충분하다.

### 고친 것 — "보이는 글자" 정의가 다섯 군데에 흩어져 있었다

프로젝트 메모에 `offset::visible` 이 그 변환을 **"독점한다"** 고 적어 두었는데
사실이 아니었다. 제품 코드 5곳이 `replace('\u{FFFC}', "")` 로 손수 다시 만들고
있었다 — `json.rs` · `screen.rs` · `main.rs` ×2 · `buffer.rs`.

지금은 결과가 같아서 아무 일도 없었다. 그러나 `visible` 이 바뀌고 그 5곳이 안
바뀌면 **기계가 받는 글자와 편집 오프셋이 어긋난다.** LLM 이 센 오프셋이 다른
자리를 가리키고, **자가검증은 그걸 잡지 못한다** — 양쪽이 같은 오프셋을 쓰므로
일치해 버린다. 바로 위에서 고친 접힌 줄 결함과 **같은 모양**이다.

전부 `offset::visible` 로 몰고, 갈라지면 걸리는 시험을 두었다. **무는지
확인했다**: `visible` 만 바꾸고 `json` 을 손수 방식으로 되돌리니 갈라진 20곳이
검출됐다.

### 고친 것 — 글자 수를 바이트 자리에 쓰고 있었다 (잠재)

글머리를 읽는 `parse_marker` 가 앞 공백을 `chars().count()` 로 세어 그 수를
`&text[indent..]` 의 **바이트** 자리에 썼다. 세는 글자가 `' '`·`'\t'` 뿐이고 둘 다
1바이트라서 **우연히** 돌았다. 세는 목록에 전각 공백(U+3000, 3바이트)이나
U+2007 을 한 줄 더하는 순간 한글 문서에서 터진다 — **이 코퍼스에 U+2007 이
74회** 있으므로 가정이 아니다. 글자 수와 바이트 수를 따로 센다.

같은 모양으로 `images.rs` 의 `BinData/BIN` 이름 파싱도 고쳤다(`rest.len() >= 4`
가 바이트인데 `&rest[..4]` 도 바이트 — 이름에 ASCII 아닌 글자가 오면 터진다).

**정직하게**: 이 둘은 시험을 붙였지만 **지금 코드에서는 물지 않는다.** 세는
글자가 ASCII 뿐이라 차이를 만들 수 없다. 시험은 요구를 적어 둔 것이고, 값은
"가정에 기대지 않게 된 것" 이다.

### 조인 것 — 시험 전제가 요구보다 느슨했다

`json_keeps_every_paragraph_and_table` 이 양쪽을 **`trim()` 해서** 비교했다.
공문서 단락은 `" ○ …"` 처럼 앞에 공백이 있고(p.hwpx 42단락 중 10개) **그 공백이
오프셋의 일부**다. trim 하고 비교하면 출구가 앞뒤 공백을 떼기 시작해도 시험이
통과한다 — 접힌 줄 결함이 기계 쪽에서 되풀이되는 길이다. 재어 보니 출구는
공백을 보존하고 있었고 **시험만 느슨했다.** 지금은 떼지 않는 것을 요구한다.

이것이 이 저장소에서 **세 번째** 같은 모양이다 — 빈 단락을 걸러냈고, 공백을
걸러냈고, 또 공백을 걸러냈다. 셋 다 "비교를 깔끔하게 하려고" 넣은 전제다.
**시험을 통과시키려고 걸러낸 것이 결함이 사는 자리다.**

### 깨끗했던 것

- **문서가 말한 길이로 바이트를 자르는 자리** — `witness.rs` 의 태그 레코드
  루프는 `p + size > buf.len()` 로 막혀 있고, `FileHeader` 는 `len() < 40` 으로
  막혀 있다. 깨진 문서로 터지지 않는다.
- **조용히 삼키는 오류** — `unwrap_or_default()` 24개·`.ok()` 19개·`let _ =`
  6개를 전수로 봤다. 전부 (a) 없는 XML 속성의 기본값이거나 (b) 임시본 정리
  코드다. 실패를 숨기는 곳은 없었다.

## 일반 텍스트 파일도 고친다

사용자 요청(2026-10-13): `hwp PLAN.md` 가 거부되었고 **간단한 텍스트는 소화해야
한다**는 지적. 지금은 열리고 고쳐지고 저장된다.

```bash
hwp PLAN.md          # 고치기로 열린다
hwp -R PLAN.md       # 읽기만
```

**왜 보기만이 아니라 고치기까지인가.** 텍스트 보기는 `less`·`cat` 이 이미 한다.
이 도구가 새로 주는 것은 **두벌식 오토마톤** — 터미널 IME 가 없는 ssh 에서 한글을
칠 수 있는 유일한 길이다. `:set ime=2` 로 켜고 `.md`·`.txt` 에 한글을 쓸 수 있다.

**백엔드가 필요 없다.** 조판기도 증인도 쓰지 않으므로 rhwp 가 깔려 있지 않은
기계에서도 텍스트는 열린다. 핀 검사도 지나지 않는다.

**대신 파일 자체가 증인이다.** 임시본에 쓰고 **되읽어** 기대와 글자 하나까지
맞춰 본 뒤에만 원본을 바꾸고 `.bak` 을 남긴다. HWP 쪽과 같은 규율이고 `--force`
는 여기에도 없다.

### 망가뜨리지 않기 위해 지키는 세 가지

| | 왜 |
|---|---|
| **UTF-8 이 아니면 열지 않는다** | 한국 텍스트 파일은 CP949(EUC-KR)가 흔하다. 억지로 읽어 저장하면 파일이 통째로 망가지는데 **열 때는 아무 표시도 나지 않는다** |
| **줄끝(CRLF/LF)을 보존한다** | CRLF 파일을 LF 로 저장하면 git diff 가 파일 전체를 바꿈으로 보고한다 |
| **마지막 줄바꿈의 유무를 보존한다** | 없던 것을 붙이거나 있던 것을 떼는 것도 내용 변경이다 |

CP949 파일은 이렇게 거부한다 — **무엇이고 어떻게 바꾸는지까지** 말한다:

```
Error: k.txt 를 열 수 없습니다 — 한글 문서가 아닙니다 (…)

Caused by:
    UTF-8 이 아닙니다 (0번째 바이트 0xC7 부터 읽을 수 없습니다).
      UTF-8 이 아닌 파일은 **열지 않습니다** — 억지로 읽어 저장하면 파일이
      망가지고, 열 때는 아무 표시도 나지 않습니다.
      CP949(EUC-KR)로 보입니다. UTF-8 로 바꾼 뒤 열어 주세요:
        iconv -f CP949 -t UTF-8 <파일> > <새파일>
```

NUL 바이트가 있으면 이진 파일로 보고 거부한다. **판단은 바이트로 한다** —
확장자는 믿지 않는다(`.md` 가 CP949 일 수 있고 확장자 없는 파일이 멀쩡한 UTF-8
일 수 있다).

### 없는 것

표(`:table`)는 거부한다 — 텍스트에 표가 없다. 그림·꾸밈·들여쓰기도 없다.
**쪽은 문서의 쪽이 아니라 우리가 50줄씩 나눈 것**이고, 상태줄이 `쪽은 우리 구분`
이라고 말한다. 폭도 문서가 정한 것이 없으니 터미널을 따르고, 그래서 상태줄이
`측정 못 함, 기본값` 이 아니라 `터미널 폭 N칸` 이라고 적는다 — 재려고 했다는
거짓을 하지 않기 위해서다.

## 접힌 줄을 되붙여 본문을 만들고 있었다 — 커서가 밀렸다

텍스트 지원을 붙이려고 원문이 필요해서 들여다보다 **이미 있던 결함**을 찾았다.

편집 버퍼의 본문을 화면 모델의 **접힌 줄**(`Block::lines`)에서 `join("")` 으로
만들고 있었다. 그런데 `wrap` 은 줄을 끊은 자리의 공백을 **버린다** — 표시에는
그게 맞다. 되붙이면 접힌 자리마다 한 칸이 사라진다:

```
wrap("a b c", 3) → ["a", "b c"] → join("") → "ab c"
                                                ↑ 공백 하나가 없다
```

코퍼스 실측 **단락 200개**가 그랬다. 결과는 표시가 아니라 **쓰기** 문제다 —
커서 오프셋이 접힌 자리 수만큼 앞으로 밀리므로, 접히는 단락에서 글자를 치면
**커서가 있는 자리가 아니라 그보다 앞에** 들어간다.

**자가검증이 이걸 잡지 못한다.** 기대값과 재생이 **같은 틀린 오프셋**을 쓰므로
둘이 일치해 저장이 통과한다. 이중 검증이 막아 주는 종류의 결함이 아니었다.

고친 방법: **원문을 모델이 들고, 접기는 표시로만 쓴다**(`ScreenDoc::paras`).
증인이 읽은 원문을 그대로 들고 나가고 버퍼가 그것을 쓴다.

**시험이 이걸 가려 주고 있었다.** `screen_model_loses_no_text_and_duplicates_none`
이 **양쪽에서 공백을 걸러내고** 비교했다(`filter(|c| !c.is_whitespace())`) — 그래서
통과하면서 바로 그 결함을 보이지 않게 했다. 빈 단락 때와 같은 모양이다: 요구가
아니라 그때의 동작을 적은 시험. 지금은
`the_paragraph_text_the_editor_edits_is_the_witness_text_space_for_space` 가
공백까지 요구하고, 결함을 일부러 되돌려 **정말 무는지 확인했다**(128개 검출).

## 말투 — 사람에게는 높임말, 기계에게는 평서체

사용자 보고(2026-10-13): **"메시지들이 어색함."** 상태줄·CLI 안내가 전부 평서체여서
도구가 사람에게 반말로 말하고 있었다. 지금 경계는 이렇다.

| 어디 | 말투 | 예 |
|---|---|---|
| 상태줄·CLI 안내·오류 | **높임말** | `되돌릴 것이 없습니다` · `크기가 필요합니다 — :table 3x4` |
| `hwp api` 의 JSON | 평서체 | `{"error":"요청이 비었다"}` |
| 문서(README·주석) | 평서체 | 이 문장처럼 |
| 시험 단정·`expect`/`panic!` | 평서체 | `assert!(…, "폭이 바뀌지 않았다")` |

가르는 기준은 **읽는 쪽이 사람인가**다. `api` 의 JSON 은 LLM·스크립트가 받는 값이라
말을 높일 상대가 없고, `expect`/`panic!` 은 개발자만 본다.

**시험은 어미를 빼고 어간으로 검사한다.** 이 전환에서 단정 13곳이 깨졌는데, 전부
`contains("없다")` 처럼 종결어미까지 박아 둔 것이었다. 시험이 요구하는 것은 "무엇을
말했는가"지 "어떤 말투인가"가 아니므로 지금은 `contains("없")` 로 쓴다 — 말투를 다시
못 박으면 다음 전환에서 또 깨진다.

**걸리는 시간을 숫자로 약속하지 않는다.** 여는 중 안내가 `(큰 문서는 수십 초가
걸린다)` 였다. 그 숫자는 실측이었지만 **10.6MB·16,384쪽 문서**의 것이고(`rhwp info`
혼자 62초), 안내가 뜨는 문턱은 1MB 다 — 그 문턱을 막 넘는 문서는 조판까지 0.19~0.35초로
끝난다(s14.hwpx 2.8MB 0.19s · s02.hwp 2.1MB 0.35s). 한쪽에서 참인 수를 다른 쪽에
그대로 쓰면 거짓이 된다. 문턱은 넉넉히 두고(멈춘 듯 보일 때 알려 주는 것이 목적이므로)
약속만 거뒀다 — `(큰 문서는 시간이 걸립니다)`.

**저장 쪽에는 아직 진행 안내가 없다.** `save()` 가 재생하고 되읽는 동안 화면이 말없이
멈춘다. 코퍼스에서는 0.12초 안에 끝나지만(s14.hwpx 2.8MB), 큰 문서에서는 여는 쪽과 같은
안내가 필요하다.

## 구조

파싱·조판·쓰기는 **[rhwp](https://github.com/edwardkim/rhwp)** (MIT) 가 한다.
우리가 만드는 것은 터미널 쪽 — 그게 비어 있는 칸이다(PLAN.md §7).

- `crates/hwp-core` — 백엔드 래퍼 + 호환성 게이트 + 독립 증인
- `crates/hwp-cli` — `hwp` 명령
- `rhwp-pin.toml` — rhwp 버전·sha256·필수 명령 고정
- `samples/` — 회귀 코퍼스(실무 문서 14개). `cargo test` 가 이걸로 돈다
- `hancom-test/` — 한컴오피스 확인 세트. `README.md` 에 확인표

**독립 증인이 따로 있는 이유**: 쓰기를 한 쪽이 그 쓰기를 검증하면 같은 버그를
두 번 통과한다. `witness` 는 컨테이너를 직접 열어 구조만 센다. 실측으로 백엔드와
단락 좌표가 일치함을 확인했다(샘플 14/14).

## 다른 컴에서 시작하기

위의 [설치](#설치)를 한 줄씩 푼 것이다 — Rust 가 없는 기계, PATH 가 안 잡히는
셸, glibc 가 오래된 배포판까지.

```bash
git clone https://github.com/k821209/hwp-vi.git && cd hwp-vi

# 1) Rust
ls ~/.cargo/bin/cargo 2>/dev/null || \
  curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --profile minimal
source "$HOME/.cargo/env"          # 이미 열려 있는 셸에는 이게 필요하다

# 2) 백엔드를 핀대로 받는다. sha256 이 다르면 설치하지 않고 멈춘다
./scripts/fetch-rhwp.sh

# 3) 빌드하고 진단
cargo build --release
./target/release/hwp doctor
```

**`zsh: command not found: cargo`** 가 나오면 PATH 문제다. rustup 이 `~/.zshenv` 에
넣어 주지만 **이미 열려 있는 셸에는 반영되지 않는다** — `source "$HOME/.cargo/env"`
하거나 터미널을 새로 열면 된다. 다음부터 자동으로 잡히게 하려면:

```bash
echo 'source "$HOME/.cargo/env"' >> ~/.zshrc
```

**맥에서 `linker 'cc' not found`** 가 나오면 명령행 도구가 없는 것이다:

```bash
xcode-select --install
```

### `sha256 불일치 — 설치하지 않는다` — 상류가 태그를 덮었을 수 있다

```
sha256 불일치 — 설치하지 않는다
  기대: 8c9d75ce14cdc3c34d3c7d843a44de3e77ab0dff04a5b189f23fea21999b4455
  실제: c4a70f5ed11b99586ee89d1ac9069145d58a0831d00e87858bb01626e2ebf313
```

**"받다가 깨졌다" 로 읽지 말 것.** 2026-10-13 에 상류가 **이미 공개한 `v0.8.7`
태그의 산출물 다섯 개를 전부 교체**했다. 버전 문자열은 그대로이고 해시만 바뀌어,
그날 새로 클론한 기계는 **모든 플랫폼에서** 설치가 거부됐다. 핀이 제 일을 한
것이다 — 없었다면 다른 바이너리로 조용히 갈아타 있었을 것이다.

**태그는 불변이 아니다.** 그러니 먼저 상류의 체크섬과 대조한다:

```bash
curl -fsSL https://github.com/edwardkim/rhwp/releases/download/v0.8.7/SHA256SUMS.txt
```

여기에 적힌 값과 `rhwp-pin.toml` 이 다르면 교체된 것이다. 그때 **해시만 고쳐
넣지 않는다** — 그러면 고정의 의미가 없고, 상류의 모든 변경을 무조건 승인하는
도장이 된다. 새 바이너리가 옛것과 같이 도는지 먼저 전수로 재고 나서 갱신한다.
그날 쟀던 것:

```bash
# 1) 명령 표면 — 빠진 기능이 있는가
diff <(./vendor/rhwp/rhwp capabilities) <(/tmp/new/rhwp capabilities)

# 2) 읽기 — 코퍼스 전수, 출력 바이트 비교
for f in samples/* hancom-test/*; do for c in info export-structure export-tables \
  export-text word-count dump-pages; do
  a=$(./vendor/rhwp/rhwp $c --json "$f" | sha256sum)
  b=$(/tmp/new/rhwp     $c --json "$f" | sha256sum)
  [ "$a" = "$b" ] || echo "DIFF $c $f"
done; done

# 3) 쓰기 — 같은 연산을 양쪽으로 돌려 산출 문서를 다시 읽어 비교
#    (**출력 경로를 같게 두어야 한다** — JSON 의 `source` 에 경로가 들어 있어
#     경로가 다르면 멀쩡한 쌍도 다르게 나온다)

# 4) 우리 시험 전체를 새 바이너리로 끼워서
HWP_RHWP_BIN=/tmp/new/rhwp cargo test --release
```

결과: `export-png` 가 **꺼짐→켜짐** 하나뿐이고 98개 명령의 나머지는 전부 동일
(빠진 기능 없음 — 상류가 PNG 내보내기를 켜서 다시 빌드한 것으로 보이고, 그것이
아래 glibc 요구가 올라간 것도 설명한다). 읽기 **138/138**, 쓰기 **30/30** 바이트
동일, 시험 **236개 전부 통과**. 이 넷이 통과했기에 핀을 갱신했다. 하나라도
어긋났다면 핀을 그대로 두고 백엔드 버전을 올렸을 것이다. 측정 기록은
`rhwp-pin.toml` 의 주석에 남아 있다.

### `version \`GLIBC_2.39' not found` — glibc 가 낡았다

```
vendor/rhwp/rhwp: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.39' not found
```

**sha256 은 맞았다.** 받은 파일이 깨진 것이 아니라, 릴리스 바이너리가 **더 새
환경에서 빌드**되어 이 리눅스의 glibc 보다 새 것을 요구하는 것이다. 공식 릴리스에
musl 정적 빌드가 아직 없다(2026-10-10 기준 x86_64·aarch64 linux, macos, windows
넷뿐). 실측 보고: WSL Ubuntu 20.04(glibc 2.31)에서 2.39 를 요구했다 — 4년 차다.

`ldd --version` 으로 지금 버전을 확인하고 둘 중 하나로 간다.

```bash
# (1) 더 새 배포판에서 쓴다 — WSL 이면 윈도우 쪽 PowerShell 에서
wsl --install Ubuntu-24.04

# (2) 소스에서 직접 빌드한다 — 그 기계의 glibc 에 링크된다
./scripts/build-rhwp.sh
```

**(2) 가 관문을 통과하는 이유**: 실행 시 관문은 sha256 이 아니라
`capabilities`(스키마 major + 필수 명령 12개)만 본다. 핀의 sha256 은 **내려받은
타르볼**에만 걸리므로, 직접 빌드한 것도 똑같이 검사받고 똑같이 쓸 수 있다.
`build-rhwp.sh` 는 핀이 정한 **태그만** 받는다(`main` 을 받으면 핀의 뜻이 없다) —
타르볼 해시 대신 git 태그를 믿는 것으로 신뢰 모델이 바뀌는 점은 분명히 해 둔다.
`cargo build` 가 몇 분 걸리고 디스크를 몇 GB 쓴다.

#### 이때 잡은 버그

우리 쪽도 틀렸다. `read_capabilities` 가 **stderr 를 버리고** "rhwp 바이너리가
맞는지 확인하라" 고만 했다 — 그런데 바이너리는 맞았고, 설명해 주는 줄은 버려진
stderr 에 있었다. 이제 ld.so 의 불만을 읽어 **가장 높은 요구치**를 집어
말한다(첫 줄의 2.35 를 집으면 그걸 맞춰 놓고 또 막힌다). `fetch-rhwp.sh` 도
받은 직후 실행해 보고, 못 돌면 못 도는 바이너리를 `rhwp.unusable` 로 치운다 —
남겨 두면 `vendor/` 가 `$PATH` 의 멀쩡한 rhwp 를 가린다.

`hwp doctor` 가 이렇게 나오면 준비가 끝났다:

```
  백엔드
    경로             vendor/rhwp/rhwp
    tool/version     rhwp 0.8.7
    schemaVersion    1.0
  ✅ 게이트 통과 — 이 백엔드를 쓸 수 있습니다.
```

**리눅스·맥(x86_64·aarch64)** 은 `fetch-rhwp.sh` 가 받는다(오래된 리눅스는 위
glibc 절을 보라). **윈도우**는 스크립트가
bash 전용이라 `rhwp-pin.toml` 의 `windows-x86_64` 해시로 직접 받아 `vendor/rhwp/`
에 풀면 된다. 백엔드를 이미 가지고 있으면 `HWP_RHWP_BIN=/경로/rhwp` 로 알려줘도 된다.

바로 해볼 것:

```bash
hwp page  <아무.hwp>              # 쪽 단위로 본문 출력
hwp toc   <아무.hwp>              # 개요 트리
hwp cells <아무.hwp>              # 표 격자와 셀 좌표
hwp json  <아무.hwp> --profile outline
hwp view  <아무.hwp>              # 페이저 (t 개요, / 검색, q 종료)
cp 원본.hwp 사본.hwp && hwp set-para 사본.hwp "0:0=바꿀 글자"
```

## 쳐도 화면에 안 나타났던 것

2026-10-10 보고: **`i` 로 글자를 쳐도 화면에 안 보이고, Enter 를 눌러야 나타난다**
(한글·영문 둘 다). 원인은 "화면을 다시 그릴지" 를 **연산 개수**로 판단한 것이었다.

같은 단락에서 이어 치는 글자는 **한 연산으로 모인다**(그게 맞는 설계다 — rhwp 에 보낼
연산은 하나여야 한다). 그래서 개수가 안 바뀌고, 첫 글자만 그려졌다. 조합 중인 자모는
더 심하다 — 커밋되기 전에는 연산이 **아예 없으므로** 영원히 안 그린다.

고친 것: 버퍼에 **판 번호**(`revision`)를 두고 보이는 상태가 바뀔 때마다 올린다.
칸 글자는 따로 센다(`cell_revision`) — 칸이 바뀌면 격자를 전부 다시 그려야 하는데,
본문 글자 하나 칠 때마다 그러면 표 서른 개짜리 문서에서 낭비다.

### 더 나쁜 것은, 내 시험이 이걸 볼 수 없었다

대화형 루프는 키마다 화면을 다시 그렸고, `--keys`(= `--frame` 으로 화면을 글로 보는
길)는 **그리지 않았다.** 둘이 따로 적혀 있었다. 그래서:

- `--frame` 출력이 **거짓말을 했다** — 실제 화면과 다른 것을 보여 줬다.
- 그 길로 돌아가는 시험이 전부 통과했다.

화면 없이 화면을 확인하는 도구가 실제와 다르면 그 도구는 쓸모가 없는 게 아니라
**해롭다.** 한 함수(`run_pager::step`)로 합쳤다 — 키를 받아 동작으로 옮기고, 적용하고,
바뀐 만큼 다시 그리는 한 걸음이다. 루프와 `--keys` 가 그 함수를 부른다.

`--keys` 가 받는 키 이름도 좁았다. `<bs>`(지우기)가 없어서 "칸 글자를 고쳐 넣는" 것을
그 길로 시험할 수 없었고, Ctrl 조합(`<c-r>`)이 없어서 다시하기가 깨진 채 있었다 —
셀 편집의 `forward` 가 `None` 을 돌려주며 "버퍼가 만든 편집이 아니다" 라고 거절했는데,
그건 셀을 버퍼가 만들지 않던 때의 말이다.

## 가로세로 대조로 찾은 것

한 문서를 한 방식으로 보는 시험은 그 조합만 지킨다. **축을 곱해서** 돌려 보면
(문서 × 읽는 방식 × 폭 정책 × 편집 종류 × 화면 크기 × 키) 손으로 쓴 시험이 통과하는
동안 살아 있던 것이 나온다. 2026-10-10 에 여섯 개를 찾았다.

| | 어떻게 틀렸나 | 어떻게 드러났나 |
|---|---|---|
| **그림이 조용히 사라졌다** | 개체가 달린 단락을 `delete-para` 하면 저장이 **성공**으로 끝나고 그림이 함께 사라졌다 (s00.hwp 단락54, 6→5개). 자가검증이 글자와 셀만 비교해서 볼 수 없었다 | 편집 종류 × 문서 전수 |
| HWPX 는 개체를 안 셌다 | OWPML 읽는 쪽이 `objects` 를 채우지 않아 HWPX 8개 문서가 전부 0개. 그래서 여백의 `◻`(못 그린 개체)가 HWPX 에서 안 떴고, 위 관문도 HWP5 에서만 걸렸다 | 개체 수 ↔ 표·그림 앵커 대조 |
| 그림이 표를 부쉈다 | 반블록 `▀▄█`·점자는 선 문자와 같은 **Ambiguous** 다. 넓게 그리는 터미널에서 두 칸이 되는데 한 칸으로 셈해서, 바깥 테두리 40칸인 표의 그림 줄이 26~35칸으로 잘렸다 | 줄 폭 불변식 × 폭 정책 |
| 덮개·안내줄이 밀렸다 | 표는 ASCII(`+ - │`→`|`)로 바꿔 뒀는데 **나머지 장식은 그 결정을 못 받았다** — 도움·메뉴 테두리, `· → ↓ —` 가 그대로였다. 넘치는 줄 **1,070 / 23,040** | 같은 불변식 |
| 빈 단락 좌표가 숨었다 | `hwp json` 이 글자가 빈 단락을 건너뛰어, 고칠 자리의 주소가 사라졌다 (s16.hwp 13/13) | 문서 × 읽는 이름 전수 |
| `witness --text` 가 말없이 잘랐다 | 60자에서 끊고 아무 표시가 없어서, 이 출력으로 저장 결과를 대조하던 **내 측정 스크립트가 틀린 불일치를 쏟아냈다** | 스스로 당했다 |

폭 정책 쪽 둘은 「표가 어긋나는 원인은 터미널의 Ambiguous 폭이다」 절에 함께 적었다 —
표에만 적용했던 ASCII 규칙을 장식 전부로 넓힌 이야기다.

### 개체가 달린 단락은 지울 수 없다

표·그림·글상자가 달린 단락을 지우면 그 개체도 함께 사라지는데, 이 도구는 개체를
만들거나 옮기지 못해서 "이렇게 되어야 한다" 를 쓸 수 없다. 즉 **검증되지 않은
쓰기**다(글자 꾸밈 쓰기·누름틀 `fill` 을 미룬 것과 같은 이유). 그래서 거부하고, 거부는
`expected` 에서 하므로 **`dryRun` 이 미리 말한다** — 쓰고 나서 "저장을 멈췄습니다" 가
아니라.

비교 단위에 **개체 수**가 들어갔다(`Snapshot.drawings`). 글자와 셀만 세던 동안 그림
삭제가 성공으로 보고되었다.

## 시험

```bash
cargo test
```

191종이 돈다. 회귀 코퍼스(`samples/`, 실무 문서 14개)가 저장소에 함께 있어서
클론한 기기에서 바로 전수 대조가 돈다:

- 백엔드가 전부 읽히는가
- **독립 증인의 단락·셀 좌표가 백엔드와 같은가** (글자까지)
- 화면 모델이 본문을 잃거나 중복하지 않는가
- 편집이 자가검증을 통과하고, 틀릴 때 **원본을 건드리지 않는가**
- `hwp json` 이 단락·표를 하나도 빠뜨리지 않는가
- **기계 쪽 입구가 사람 쪽과 같은 범위를 가지는가** — 섞인 편집 한 요청이 한 번만
  저장되는지, `dryRun` 이 원본의 sha256 을 건드리지 않는지, `--capabilities` 가
  가리키는 `op`·`read` 이름이 실제로 받는 이름인지
- **가로세로** — 문서 × 읽는 이름 8개, 편집 종류 7개 × 형식 2개(저장까지 가서 증인이
  재확인), 모든 그리기개체가 그 단락에 세어지는지, 그림 글리프가 어느 폭 정책에서도
  1칸인지, 넓은 터미널에서 **우리 장식이** 줄을 밀지 않는지

코퍼스를 비우면 그 시험들은 건너뛰는데, **cargo 가 건너뜀 메시지를 숨겨서 통과처럼
보인다.** 그래서 `hwp doctor` 가 코퍼스 문서 수를 함께 알려준다. 직접 보려면
`cargo test -- --nocapture`.

자기 문서를 더 넣어도 된다 — `samples/` 에 `.hwp`·`.hwpx` 를 떨어뜨리면 그 문서들에
대해서도 같은 대조가 돌아간다.

여백 표시: `↳` 앞 쪽에서 이어진 단락 · `*` 고친 단락 · `◻` **우리가 못 그린
개체**(글상자·수식 등). 표와 그림은 아래에 그리므로 표시하지 않는다 — 처음엔
인라인 컨트롤이 있으면 다 붙였다가 구역 정의·쪽번호까지 걸려 "그림이 있는데 안
보인다" 는 오해를 불렀다.

`◻` 는 2026-10-10 까지 **HWPX 에서 한 번도 뜨지 않았다.** OWPML 읽는 쪽이 개체를
세지 않아서다 — 기능이 반만 사는 모양은 "안 된다" 보다 알아채기 어렵다.

**이 저장소는 private 으로 둔다.** `samples/` 와 `hancom-test/` 의 문서는 실제 업무
문서이고 사람 이름과 기관 내용이 들어 있다. 한번 커밋되면 git 히스토리에 남으므로
공개로 바꾸면 같이 공개된다 — 공개할 생각이면 **먼저 이 파일들을 히스토리에서
걷어내야 한다**(`git filter-repo` 등).

자기 문서로 코퍼스를 만들려면 `.hwp`·`.hwpx` 를 `samples/` 에 넣기만 하면 된다.
그러면 전수 대조가 그 문서들에 대해 돌아간다:

- 백엔드가 전부 읽히는가
- **독립 증인의 단락·셀 좌표가 백엔드와 같은가** (글자까지)
- 화면 모델이 본문을 잃거나 중복하지 않는가
- 편집이 자가검증을 통과하고, 틀릴 때 **원본을 건드리지 않는가**
- `hwp json` 이 단락·표를 하나도 빠뜨리지 않는가

백엔드 핀(`rhwp-pin.toml`)을 올릴 때는 이 시험을 먼저 통과시킨다. 후보 하나가
README 상으로는 멀쩡했고 실제로는 14개 중 3개만 읽혔다(PLAN.md §7).

## 한컴오피스 확인

자체 검증(독립 증인 + 테스트 82종)은 **구조**가 맞는지만 안다. 한컴이 그 구조를
받아들이는지는 한컴만 판정할 수 있다. `hancom-test/` 에 쓰기 경로별로
하나씩 따로 만든 시험 파일(T0~T7, 각자 `.bak` 원본 포함)과 확인표가 있다 — 하나가 안 열려도 어느 경로가
문제인지 바로 알 수 있게 나눠 뒀다.

```bash
# 시험 파일을 다시 만들려면 (samples/ 가 있어야 한다)
hwp set-cell  T1.hwp  "0:1:1=값"          # 표 셀 쓰기
hwp set-para  T2.hwp  "0:10=새 단락 글자"   # 본문 글자 바꾸기
hwp para      T5.hwp  --insert 0:11 --delete 0:1
```

## 컴파일 시점에 박아 넣는 파일은 소스다

`include_str!` 이 가리키는 파일은 `.gitignore` 에 걸려서는 안 된다. 2026-10-11 에
한자 표를 `vendor/` 에 두었는데 그 자리는 `scripts/fetch-rhwp.sh` 가 **받아 오는**
자리이고 무시 목록에 있다. `git add -A` 가 조용히 빼놓았고, 커밋은 통과했고, 이
기계에서는 파일이 있어서 빌드도 됐다 — **새로 클론한 기계에서만** 터졌다.

```
error: couldn't read `crates/hwp-core/src/../../../vendor/hanja/hanja-syllables.txt`
  --> crates/hwp-core/src/hanja.rs:22:21
```

코퍼스 시험이 이제 `crates/` 아래의 모든 `include_str!`·`include_bytes!` 가 가리키는
파일이 **git 이 추적하는 것인지** 본다. 걸리면 이유까지 말한다:

```
hanja.rs 의 include_str!("../../../vendor/hanja/…" → `vendor/hanja/…` 이 git 에 없다
  (.gitignore 에 걸렸을 것이다 — 새 클론에서 빌드가 깨진다)
```

새 데이터를 넣을 때 **깨끗한 클론에서 빌드해 보는 것**도 같이 한다 —
`git clone . /tmp/x && cd /tmp/x && cargo build --release`.
